# Подсказка для агентов (Cursor / AI)

## Главное правило

Если пользователь пишет **«по ТЗ»**, **«продолжай по ТЗ»** и не называет конкретный документ — **точка входа одна**: [`docs/spec/TZ_FULL_UNIFIED.md`](docs/spec/TZ_FULL_UNIFIED.md). Этот файл — канонический и единственный источник истины. В нём есть:

- раздел **A** — MVP-объём (теги `[MVP]`, P0/P1, критерии приёмки релиза);
- раздел **B** — полный объём (vNext, теги `[v1.1] / [v1.2] / [v2.0]`, конкурентный паритет);
- раздел **C** — где смотреть текущий статус (живые источники, не дублировать);
- раздел **D** — фазы реализации (Phase 0..10);
- раздел **E** — обязательные правила доработки (разд. 36 vNext, шесть вопросов);
- раздел **G** — карта канонических документов и запрет на дубли;
- раздел **H** — шаблон финального отчёта в PR.

Не разбирайте `PLATFORM_VNEXT_UPGRADE_SPEC.md` целиком как чек-лист кода: туда заходите по ссылкам из раздела **B** для подробностей конкретного блока. Разд. 36 vNext (ограничения) уже сжат в коде — `backend/app/core/product_spec.py` (`ARCHITECTURE_RULES`, `ENGINEERING_RULES`, `PRODUCT_UX_RULES`, `SIX_QUESTIONS`).

## Расширение объёма (Дополнения №1–№4, разделы 49–74)

Кроме базового объёма, действует **расширение** — раздел **B-NEXT** в `TZ_FULL_UNIFIED.md`. Это **часть полного объёма (раздел B)**, а не отдельные документы; при «продолжай по ТЗ» эти требования подхватываются наравне с остальными. Исходники дополнений — в `docs/spec/appendix/`, но источник истины — канон в репозитории. Приоритет волн — `PLATFORM_VNEXT_IMPLEMENTATION_PLAN.md` (фазы 11–20); REQ-ID и статусы — `TZ_COVERAGE_MATRIX.md`; программные константы — `backend/app/core/product_spec.py`.

- **Бизнес-расширение [vNext-BIZ]** (Доп. №1–№2, разд. 49–62): аутсорсинговый контур (Managed Clients), продажа/аренда (reseller-иерархия, white-label), мультидисциплинарность (ПБ/ПромБез/Экология/ГО-ЧС/БДД), простой UX (UX-бюджет + чек-лист приёмки экрана) и модульная поставка (entitlements). Фазы 11–15.
- **Security-расширение [vNext-SEC]** (Доп. №3, разд. 63–70): модель угроз новых поверхностей, AppSec/OWASP (найденный XXE — **уже закрыт**, `backend/app/core/xml_security.py`), RLS как второй рубеж изоляции, ПДн/152-ФЗ, единая политика секретов, security-gate в CI. Приоритет **выше** бизнес-фаз — Phase 16.
- **Ops-расширение [vNext-OPS]** (Доп. №4, разд. 71–74): импорт-фреймворк, жизненный цикл клиента (онбординг → офбординг), версионирование API + deprecation, zero-downtime деплой. Фазы 17–20.

## Порядок работы (README → ТЗ → отчёт → код)

Полная инструкция: [`docs/AI_AGENT_WORKFLOW.md`](docs/AI_AGENT_WORKFLOW.md). Кратко:

1. `README.md` (ссылки на ТЗ, релиз, runbook).
2. **`docs/spec/TZ_FULL_UNIFIED.md`** — раздел A (для MVP-задач) или раздел B (для vNext-задач).
3. **`AI_IMPLEMENTATION_REPORT.md`** — журнал волн / handoff. Берите следующий шаг из последнего блока «Last Agent Handoff» / `Next Steps`.
4. Сверка статуса:
   - MVP — `docs/audit/TZ_COVERAGE_MATRIX.md`;
   - vNext-фаза — `docs/roadmap/PLATFORM_VNEXT_IMPLEMENTATION_PLAN.md`.
5. Только потом — код.
6. После волны: обновите `AI_IMPLEMENTATION_REPORT.md` (handoff), при необходимости — `TZ_COVERAGE_MATRIX.md`, `CHANGELOG.md`. README правьте только если изменились ссылки/запуск/навигация.

## Запреты (кратко)

- Не плодить альтернативные ТЗ-файлы / roadmap'ы / отчёты по статусу.
- Не дублировать требования между `TZ_FULL_UNIFIED.md` и `PLATFORM_VNEXT_UPGRADE_SPEC.md`.
- Не ломать существующие API / роли / миграции / сценарии без обоснования и совместимости.
- Не выдумывать требования — подтверждайте из канонического ТЗ или из кода.
- Кандидаты на удаление документации — только в `docs/CLEANUP_CANDIDATES.md` и в handoff `AI_IMPLEMENTATION_REPORT.md`.

Подробно — раздел `0.3` и `G` в `docs/spec/TZ_FULL_UNIFIED.md` и `docs/AI_AGENT_WORKFLOW.md`.
