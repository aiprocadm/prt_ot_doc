# P10-06 СИЗ склад — срез «Мобильная выдача (корзинная, online-first)» — Design

**Дата:** 2026-07-05
**Контур:** P10-06 СИЗ склад (Section B, `docs/roadmap/PLATFORM_VNEXT_IMPLEMENTATION_PLAN.md`)
**Предшественники (влиты в main):** журнал движений (`PPEStockMovement`, `wa04`, FIFO-списание, PR #720) → мин-остаток/дефицит (`wa05`, `/stock/shortages`, PR #721) → инвентаризация (`wa06`, PR #722) → перемещения между локациями (`wa07`, PR #724) → **поставщики** (`PPESupplier`, `wa08`, `/stock/reorder`, PR #725, влит).
**Driver:** brainstorming → writing-plans → subagent-driven-development.
**Особенность среза:** **чисто фронтовый** — бэкенд выдачи СИЗ уже полон (`POST /ppe/issues` → `issue_ppe_item` + `deplete_for_issue` FIFO). Новых эндпоинтов, схем, моделей и **миграций НЕТ**. Значит **OpenAPI baseline и PG16-гейт не трогаются**; гейты среза — только фронтовые (`tsc` / `vitest` / `vite build`).

## Цель

Дать полевую (мобильную, touch-first) выдачу СИЗ: кладовщик/мастер на телефоне быстро находит
работника, набирает ему **набор (комплект)** позиций СИЗ в корзину и выдаёт всё разом — поверх уже
готового API выдачи и честного остатка. Сегодняшний экран выдачи (`PpePage.tsx`) — десктопная панель с
`<select>`-дропдаунами и разовой выдачей одной позиции; для поля он неудобен.

Срез **online-first**: требует живого соединения. Полноценный офлайн (IndexedDB-очередь, replay,
серверная идемпотентность, conflict-inbox) — **осознанно отдельный будущий срез** (см. «Вне объёма»);
здесь закладывается только минимальный online-guard от двойной выдачи (single in-flight lock +
per-line success tracking), без серверных изменений.

## Принятые решения (brainstorming, 2026-07-05, AskUserQuestion)

1. **Срез = мобильная выдача** (следующий пункт P10-06 после поставщиков; альтернатива «бюджет
   безопасности» отложена).
2. **Офлайн-объём = online-first.** Мобильно-оптимизированный поток поверх готового `POST /ppe/issues`;
   минимальный groundwork (guard от двойной выдачи), **очередь НЕ строим**. (Отклонён «полный офлайн» —
   2-3 среза работы: весь отсутствующий фронтовый IndexedDB-слой + серверная миграция идемпотентности +
   PWA-capabilities + conflict-UI, высокий риск двойной выдачи. Отклонён «только groundwork» — добавлял
   серверную миграцию идемпотентности + регистрацию в `/pwa/bootstrap`; пользователь выбрал меньший
   online-first.)
3. **Модель потока = корзина/комплект.** Работник → добавить несколько позиций в корзину (кол-во /
   опц. партия) → обзор → выдать всё разом (N вызовов `POST /ppe/issues`, обработка частичного отказа).
   (Отклонён «единичная выдача с повтором» — почти не отличается от адаптива `PpePage`. Отклонён
   «norm-driven комплект по нормам 766н» — самый ценный, но самый большой срез: нужен вывод норм/
   карточки на мобильный + богатый UI; вынесен в follow-up.)
4. **Идентификация работника = поиск/typeahead** по имени/должности, крупные touch-строки. (Отклонён
   «QR/штрих-скан бейджа» — зависимость от QR-библиотеки + инфраструктуры бейджей с резолвом кода;
   вынесен в follow-up, добавляется без переделки потока.)
5. **Подпись = только подтверждение, без подписи.** Экран «обзор → выдать всё» и есть подтверждение;
   захват подписи (canvas → `signature_doc_ref` + файловое хранилище) — follow-up (компл. значимо, но
   трогает create-путь).

## Архитектура

Всё — на фронте, поверх существующего API. Backend не трогается совсем.

### Слой 0 — что переиспользуется как есть (ничего не менять)

- **`opsApi.getPpeOverview()`** (`frontend/src/api/ops.ts`) → `{ items: PpeItemDto[], persons: PersonDto[],
  issues, expiring }`. Источник каталога позиций и списка работников. (Грузит по 100 записей — для MVP
  достаточно; серверный поиск работников — follow-up при больших тенантах.)
- **`opsApi.createPpeIssue({ person_id, item_id, quantity })`** → `PpeIssueDto`. Единственный мутатор.
  `wear_days`/`expires_at`/`issued_at` **не передаём** — бэкенд авто-считает `expires_at` из
  `item.default_wear_days`.
- **`warehouseApi.listLevels()`** (`frontend/src/api/warehouse.ts`) → `StockLevelDto[]`
  (`item_id`, `item_name`, `total_quantity`, `batch_count`). Источник остатка «на руках» per item.
- **`PERMISSIONS.PPE_ISSUE`** (`ppe.issue`) — гейт маршрута/кнопки.
- **`PersonDto`** (`frontend/src/types/dto/persons.ts`): `full_name`, `position`, `status`
  (`active|inactive|dismissed`). Поиск — по `full_name`+`position`; по умолчанию показываем только
  `status === "active"` (выдача уволенному — нонсенс; переключатель «показать всех» — опционально).
  **Табельного номера в DTO нет** — поиск по номеру = follow-up (нужно поле в DTO/бэкенде).

### Слой 1 — маршрут + точка входа

- Новый маршрут **`/ppe/issue`** в `frontend/src/router/routeGroups.tsx`, отдельной группой
  `{ permission: PERMISSIONS.PPE_ISSUE, routes: [<Route key="/ppe/issue" path="/ppe/issue"
  element={<MobileIssuePage />} />] }`. (Гейт по `PPE_ISSUE`, не `PPE_VIEW` — это операция выдачи.)
- **Обнаруживаемость:** на `PpePage.tsx` добавить кнопку-ссылку «Мобильная выдача» → `/ppe/issue`
  (видна тем, у кого `PPE_ISSUE`; десктоп-пользователи тоже находят экран). Существующая форма быстрой
  выдачи на `PpePage` **остаётся** (не ломаем).
- Страница mobile-first (одноколоночный layout, крупные тап-цели), но работоспособна на любой ширине.

### Слой 2 — файловая раскладка (мелкие изолированные модули, ни один не растёт)

```

frontend/src/pages/ppe/mobile-issue/WorkerSearch.tsx   # шаг 1: typeahead работника

frontend/src/pages/ppe/mobile-issue/IssueCart.tsx      # корзина: строки с qty-степпером/удалением
frontend/src/pages/ppe/mobile-issue/IssueReview.tsx    # шаг 3+результат: «Выдать всё (N)» + per-line ✓/✗
```

### Слой 3 — состояние и поток (`useMobileIssue`)

**Типы (`types.ts`):**

```ts
export type MobileIssueStep = "worker" | "items" | "review";

export type CartLine = {
  item_id: string;
  item_name: string;
  quantity: number;          // ≥1
  on_hand: number | null;    // из listLevels; null = остаток неизвестен (флаг warehouse off / нет данных)
};

export type IssueResultLine = {
  item_id: string;
  item_name: string;
  quantity: number;
  status: "ok" | "error";
  error?: string;            // сообщение для строки с ошибкой
};
```

**Состояние хука:**
- `step: MobileIssueStep` (навигация вперёд/назад; на «review» — кнопка «Назад» к «items»).
- `worker: PersonDto | null`.
- `cart: CartLine[]`.
- `stockAware: boolean` — удалось ли загрузить `listLevels()` (см. слой 4).
- `levels: Map<item_id, total_quantity>`.
- `submitting: boolean` — single in-flight lock (guard от двойной выдачи).
- `results: IssueResultLine[] | null` — после первой попытки выдачи.
- производные: `persons`, `items` из `getPpeOverview`; loading/error загрузки.

**Логика корзины:**
- Добавление уже присутствующей позиции → **инкремент qty существующей строки** (корзина не плодит дубли).
- qty-степпер `−`/`+` (min 1); удаление строки; очистка корзины при смене работника.
- Если `stockAware` и `quantity > on_hand` → мягкое предупреждение на строке (не блок — бэкенд всё равно
  проверит; при флаге off предупреждения нет).

**Submit («Выдать всё»):**
```
guard: if submitting → no-op; set submitting=true
for каждой строки корзины ПОСЛЕДОВАТЕЛЬНО:
    try createPpeIssue({person_id: worker.id, item_id, quantity}) → result ok
    catch e → result error (сообщение из ответа: нехватка/валидация)
собрать results[]; set submitting=false
```
- **Частичный отказ:** успешные строки помечаются `ok` и **удаляются из корзины**; в корзине остаются
  только `error`-строки → повторная «Выдать всё» переотправит **только неудачные** (успешные не
  дублируются даже без серверной идемпотентности — это и есть online-guard).
- Все строки `ok` → экран успеха («Выдано N позиций работнику X»), кнопка «Новая выдача» (сброс).

### Слой 4 — stock-awareness и graceful degradation

Зеркалит семантику `deplete_for_issue` (no-op при выключенном флаге `warehouse`):
- При маунте пробуем `warehouseApi.listLevels()`.
  - **Успех** (флаг `warehouse` ON) → `stockAware=true`; в `ItemPicker` показываем бейдж «на руках: N»,
    в корзине — предупреждение при `qty > on_hand`.
  - **Ошибка 404/403** (флаг OFF или нет доступа) → `catch` → `stockAware=false`; экран работает в
    режиме «без остатков»: выдача всё равно проходит (создаётся `PPEIssue` без списания — как сегодня на
    `PpePage`). **Не показываем ошибку загрузки остатков как фатальную** — деградируем тихо.
- Каталог позиций (`getPpeOverview`) грузится всегда, независимо от флага.

### Слой 5 — инвариант честного остатка (не трогается)

Новых мутаторов нет. Любая выдача идёт через штатный `create_issue → deplete_for_issue`
(FIFO, `ref_id = issue.id`, `batch.quantity` меняется только в `_write_movement`). Срез **не касается**
`stock.py`/`operations.py`/моделей/схем/роутов — только фронт вызывает готовый эндпоинт.

## Обработка ошибок / edge-cases

| Случай | Поведение |
|---|---|
| `getPpeOverview` упал (сеть) | экран ошибки загрузки с кнопкой «Повторить» |
| `listLevels` упал (флаг off/403/404) | тихая деградация: `stockAware=false`, выдача без остатков (как `PpePage`) |
| нет работников / пустой каталог | пустые состояния с подсказкой |
| работник `dismissed`/`inactive` | по умолчанию скрыт из поиска (только `active`); опц. «показать всех» |
| повторное добавление той же позиции | инкремент qty существующей строки корзины (без дублей) |
| `qty > on_hand` (stock-aware) | мягкое предупреждение на строке; выдача не блокируется (бэкенд проверит) |
| нехватка остатка при выдаче | бэкенд `400` → строка результата `error` с сообщением, остаётся в корзине для повтора |
| двойной тап «Выдать всё» | `submitting` lock: второй вызов — no-op |
| частичный отказ (часть строк ok, часть error) | ok-строки удаляются из корзины; повтор шлёт только error-строки (нет двойной выдачи) |
| смена работника с непустой корзиной | подтверждение + очистка корзины |
| флаг `warehouse` off | выдача работает, остатки/бейджи скрыты |

## Явно ВНЕ объёма (следующие срезы / follow-up P10-06)

- **Офлайн-выдача целиком:** фронтовый IndexedDB-очередь + replay-on-reconnect; серверная миграция
  идемпотентности (unique на `PPEStockMovement(tenant_id, batch_id, kind, ref_id)` при `kind='issue'`

- **QR/штрих-скан бейджа работника** (QR-библиотека + резолв кода → person + рендер бейджей).
- **Захват подписи** (canvas → `signature_doc_ref` + файловое хранилище + обработка на create).
- **Norm-driven комплект по нормам 766н** (вывод карточки норм/выданного/просроченного на мобильный →
  выдача недостающего/просроченного в тап; переиспользует `build_personal_card_766n`).
- **Per-line выбор партии на мобильном** (сейчас только авто-FIFO; `batch_id` не отправляем — на фронте
  `CreatePpeIssuePayload` его и нет).
- **Серверный поиск работников** (сейчас клиентский фильтр по первым 100 из `getPpeOverview`).
- **Поиск по табельному номеру** (нет поля в `PersonDto`).
- **Бюджет безопасности** — оставшийся пункт P10-06 после этого среза.

## Анти-грабли

- **Это фронтовый срез:** НЕ создавать роуты/схемы/модели/миграции; НЕ пере-снимать OpenAPI baseline;
  PG16-гейт не запускать. Гейты — `tsc`/`vitest`/`vite build`.
- **`createPpeIssue` не принимает `batch_id`** во фронтовом `CreatePpeIssuePayload` — авто-FIFO по
  умолчанию; не выдумывать поле (per-line партия — follow-up, потребует расширения DTO).
- **`listLevels` 404 при флаге off** — обязательно `try/catch` с тихой деградацией, иначе весь экран
  падает на тенанте без склада (выдача обязана работать и без флага).
- **Частичный отказ:** удалять из корзины ТОЛЬКО `ok`-строки перед возможным повтором — иначе повтор
  переиздаёт успешные (двойная выдача без серверной идемпотентности).
- **Guard от двойного тапа:** блокировать submit флагом `submitting`, кнопку дизейблить/показывать
  «Выдаётся…» — быстрый мобильный поток провоцирует двойные тапы.
- **Только `active` работники по умолчанию** — иначе список замусорен уволенными; выдача уволенному —
  ошибка данных.
- **Кнопку-ссылку на `PpePage` добавлять аддитивно** — не ломать существующий `PpePage.test.tsx`
  (при необходимости обновить ассерт).
- **i18n:** новые строки — через существующий механизм (`frontend/src/i18n/`), не хардкодить (сверить
  паттерн с соседними страницами).
- **Операционка (из прошлых handoff):** в git-worktree нет `node_modules` — фронт-тулчейн поднять
  `npm ci --prefer-offline`; vitest/tsc/build гонять через PowerShell-инструмент; холодных бэкенд-
  импортов в этом срезе нет (тесты чисто фронтовые → быстрые).
