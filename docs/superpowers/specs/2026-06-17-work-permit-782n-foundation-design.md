# Дизайн: Наряд-допуск на высоте (782н) — Ф1 «модель + экран»

- **Дата:** 2026-06-17
- **Контур:** Наряды-допуски §16, эталон «работа на высоте» (Приказ Минтруда № 782н).
- **Этап:** Ф1 из программы Ф1→Ф4 (Ф2 — целевой инструктаж + подписи ПЭП; Ф3 — ежедневный допуск / продление / изменения состава / закрытие с подписями; Ф4 — печатный бланк 782н). Остальные виды работ (902н/1479/903н…) — тиражирование после эталона.
- **Полнота стека:** Ф1 — **full-stack** (расширение модели + схем + сервиса + миграция + фронтенд). Это НЕ «UI поверх готового».
- **Источники:** [Приказ 782н — КонсультантПлюс](https://www.consultant.ru/document/cons_doc_LAW_371453/), [текст Правил — Гарант](https://base.garant.ru/75062122/53f89421bbdaf741eb2d1ecc4ddb4c33/).

## 1. Контекст и цель

Backend наряда-допуска (`WorkPermit` + `WorkPermitMember` + `WorkPermitEvent`, FSM `draft→issued→suspended↔issued→closed/cancelled`, гейт готовности бригады, события) уже на `main`, но хранит только «скелет» полей и не имеет экрана. Ф1 даёт **рабочий экран наряда** и **расширяет модель** под описательные секции официальной формы 782н, чтобы наряд можно было завести «по форме». Подписи, ежедневная эксплуатация и печать — следующие этапы.

Переиспользуем готовое: словари ролей/видов работ/статусов/событий (`domains/work_permits/lifecycle.py`), весь фронтенд-инструментарий (`RegistryTable`, `RegistryPageHeader`, `LoadingScreen`, `ErrorState`, `EmptyState`, `StatusBadge`, `Can`, `Dialog`, `Input`, `Label`, `Button`) и конвенции из только что сделанного экрана личных допусков (Л1, PR #668).

## 2. Объём

**В объёме (Ф1):**
- Расширение модели `WorkPermit` описательными полями 782н (аддитивная миграция).
- Расширение схем/сервиса/роутов наряда новыми полями (create/update/read).
- Экран `/work-permits` (список + счётчики + фильтры) и `/work-permits/:id` (карточка).
- Создание/редактирование черновика (форма по секциям 782н), удаление черновика.
- Управление бригадой (добавить/убрать участника с ролью — только в черновике).
- Действия жизненного цикла: выдать (с проверкой готовности), приостановить, возобновить, закрыть, отменить, продлить (одна дата — журнал продлений в Ф3).
- Панель готовности бригады (`GET /readiness`) и журнал событий (`GET /events`) — только просмотр.
- Только роль `admin`.

**Вне объёма (следующие этапы):**
- Ф2: целевой инструктаж + подписи членов бригады и ответственных (ПЭП).
- Ф3: ежедневный допуск (таблица), журнал продлений, изменения состава бригады, закрытие с подписями.
- Ф4: печатный бланк 782н (DOCX-шаблон → PDF + фирменный бланк).
- Мероприятия как таблицы «наименование/срок/ответственный» (в Ф1 — текстовые блоки по секциям; **сознательное решение**, печать примет текст).
- Фото при действиях (камера — мобильный экран, отдельно).
- Тиражирование на другие виды работ.

## 3. Аудитория и права

- Роль `admin` (специалист по ОТ). Backend `/work-permits` уже гейтит `required_roles=["admin"]` на чтение и запись.
- Фронтенд: новые коды `WORK_PERMIT_VIEW = "work_permit.view"` (меню/маршрут/страница) и `WORK_PERMIT_MANAGE = "work_permit.manage"` (кнопки). У роли `admin` есть `ALL_PERMISSIONS` → коды получит только admin. Backend не меняем по правам.

## 4. Расширение модели (backend)

Аддитивная миграция `wp02` (цепочка от `wp01` или истинного head — определить в плане; имена таблиц литералами; honest downgrade удаляет добавленные колонки). Новые колонки у таблицы `work_permit` (VARCHAR/TEXT/JSON, **не PG-enum** — конвенция репо):

| Колонка | Тип | Секция 782н |
|---|---|---|
| `subdivision_text` | VARCHAR(255), null | подразделение (шапка) |
| `content_text` | TEXT, null | содержание/объём поручаемой работы |
| `conditions_text` | TEXT, null | условия проведения работ |
| `safety_systems` | JSON, null (list[str]) | системы обеспечения безопасности (мультивыбор) |
| `measures_before_text` | TEXT, null | мероприятия до начала работ |
| `measures_during_text` | TEXT, null | мероприятия в процессе работ |
| `special_conditions_text` | TEXT, null | особые условия проведения |
| `ppe_text` | TEXT, null | перечень СИЗ |

Существующие поля остаются: `number`, `work_type`, `zone_text`, `site_id`, `equipment_text`, `hazards_text` (опасные факторы), `measures_text` (legacy — оставляем, новой формой не используется), `planned_start/end`, `status`, `opened_at/closed_at/suspended_at`, `members[]`.

Опасные факторы — `hazards_text` (есть). Ответственные лица — это `WorkPermitMember` с ролями (`issuer`=выдающий, `supervisor`=ответственный руководитель, `admitter`=допускающий, `foreman`=производитель работ, `observer`=наблюдающий, `member`=член бригады); словарь уже есть, подписи — Ф2.

**Словарь систем безопасности (для высоты, фиксированный, VARCHAR-коды):**
`restraint` (удерживающие) · `positioning` (позиционирования) · `fall_arrest` (страховочные) · `rescue_evacuation` (для эвакуации и спасения) · `access` (для подъёма/спуска). Валидация в схеме: каждый элемент `safety_systems` ∈ словарь.

## 5. Расширение схем/сервиса/роутов (backend)

- `backend/app/schemas/work_permit.py`: добавить новые поля в `WorkPermitCreate`, `WorkPermitUpdate`, `WorkPermitRead`. Валидатор `safety_systems` (каждый код ∈ словарь). Чистый помощник `is_safety_system(code)` в `domains/work_permits/lifecycle.py`.
- `backend/app/domains/work_permits/service.py`: `create_work_permit`/`update_work_permit` принимают и сохраняют новые поля (passthrough, draft-only edit как сейчас).
- `backend/app/api/routes/work_permits.py`: `_permit_read` и create/patch прокидывают новые поля. Контракт действий/гейта/готовности/событий не меняется.

Существующие контракты (для справки): list `GET /work-permits?status=&site_id=&work_type=&limit&offset`; CRUD; `members` add/remove; `issue/suspend/resume/close/cancel/extend`; `readiness`; `events`. Потолок списка `le=200` (как у `/permits`).

## 7. Секции формы создания/редактирования

- **Основное:** вид работ (для эталона — «работа на высоте»), номер (необяз.), подразделение, площадка (выбор), зона, плановые сроки (начало/окончание).
- **Содержание и условия:** содержание/объём (`content_text`), условия (`conditions_text`).
- **Опасные факторы:** `hazards_text`.
- **Системы безопасности:** мультивыбор (5 значений, для высоты).
- **Мероприятия:** до начала (`measures_before_text`), в процессе (`measures_during_text`), особые условия (`special_conditions_text`).
- **СИЗ:** `ppe_text`.

Валидация (zod): вид работ и зона — обязательны (как в backend). Серверные ошибки полей — через `applyApiFieldErrorsToForm`. Редактирование/удаление/состав бригады — только в статусе `draft` (FSM backend; 409 → понятный `toast`).

## 8. Логика статусов и действий (зеркало FSM)

- `draft`: Изменить, Удалить, Бригада (+/−), **Выдать** (проверка готовности; 409 `WORK_PERMIT_BLOCKED` → показать нарушения), Отменить.
- `issued`: Приостановить, Закрыть, Продлить, Отменить.
- `suspended`: Возобновить, Закрыть, Отменить.
- `closed`/`cancelled`: действий нет.

Бейдж статуса (`StatusBadge`): draft (нейтральный) / issued (info) / suspended (warning) / closed (success) / cancelled (secondary).

## 9. Готовность и события

- Панель готовности: `GET /readiness` → зелёно «бригада готова» или список нарушений (ФИО + роль + причина из кода нарушения; маппинг известных кодов на RU + fallback на сырой код).
- Журнал событий: `GET /events` → лента (тип события RU + дата/время + заметка). Только просмотр.

## 10. Обработка ошибок

- Загрузка списка/карточки упала → `ErrorState` + «Повторить».
- Пусто → `EmptyState` + подсказка создать наряд.
- 409 `WORK_PERMIT_TRANSITION_INVALID` (действие не по FSM) → `toast.error` + reload.
- 409 `WORK_PERMIT_BLOCKED` (выдача при неготовой бригаде) → показать нарушения (в панели/тосте) + reload.
- 404 (наряд/участник удалён параллельно) → `toast.error` + reload/возврат к списку.
- 422 (невалидный код вида работ/роли/системы безопасности) недостижим из UI (выбор из словарей).

## 11. Тестирование

- Backend: `wp02` миграция-guard (цепочка/состав колонок/downgrade); сервис create/update с новыми полями; API create→read возвращает новые поля; валидатор `safety_systems` (невалидный код → 422).
- Frontend: `WorkPermitsPage.test.tsx` (рендер списка, пусто, гейт `work_permit.manage` на «Новый наряд»); `WorkPermitDetailPage.test.tsx` (секции отображаются, набор действий по статусу, скрытие действий без права).

- Прогон: Py3.12 если доступен, иначе доступный Python с отметкой о версии (CLAUDE.md).

## 12. Критерии приёмки

1. Миграция `wp02` аддитивна, downgrade честный; guard зелёный.
2. `POST /work-permits` принимает и `GET` возвращает все новые поля 782н; невалидная система безопасности → 422.
3. `/work-permits` и `/work-permits/:id` доступны только admin; список с фильтрами/счётчиками работает.
4. Черновик можно завести по всем секциям 782н, отредактировать, собрать бригаду; действия жизненного цикла работают; готовность и события видны.
5. Действия показываются по правилам FSM; 409/404 обрабатываются понятно.
6. Тесты (backend cohort + 2 фронт-теста) зелёные; сборка фронта без ошибок типов/линта.

## 13. Открытые вопросы

Нет. Мероприятия — текстовые блоки по секциям (решение принято; таблицы — возможное уточнение позже). Системы безопасности — фиксированный словарь для высоты; другие виды добавят свои на этапе тиражирования.
