# Тарифные планы тенантов (подписка)

Дата: 2026-07-21. Ветка: `feat/tenant-subscription-plans`. Продолжает
`feat/tenant-management` (управляющий тенант, PR #766).

## Задача

Платформа продаётся по подписке. Управляющему тенанту нужен понятный способ:
(1) заводить клиентов-тенантов, (2) выдавать им доступ к функциям пачкой — через
**тарифные планы**, (3) задавать лимиты. Плюс убрать поток ошибок `TENANT_INVALID`.

## Причина ошибок `TENANT_INVALID` (исправлено)

`frontend/src/config/tenants.ts` держал 4 захардкоженных тенанта, 3 из которых
(`severstroy`, `ural`, `promengineering`) в БД не существуют. Форма входа предлагала их
как подсказки; выбор любого → `X-Tenant has invalid value` на каждом запросе (проверка
в `backend/app/middleware/tenant.py`, ищет тенанта по `slug`/`code`). Оставлен только
реальный `demo`; поле входа свободное — админ нового тенанта вводит свой слаг.

## Тарифные планы

Каталог — в коде (`backend/app/modules/subscription/plans.py`), не в БД:

| План (`code`) | Функции | Лимиты (док/мес · МБ · задач) |
|---|---|---|
| Базовый (`free`) | committees, contractors, medical | 500 · 5120 · 2 |
| Про (`pro`) | + report_builder, budget, sout | 5000 · 20480 · 4 |
| Всё включено (`enterprise`) | + rules_engine, warehouse (все 8) | 50000 · 102400 · 8 |

Все 8 кодов функций — реальные гейты: каждый проверяется через
`is_feature_enabled(<code>)` в своём роутере и блокирует доступ (404), если функция
выключена. Значит, применение плана реально открывает/закрывает функции.

## Хранение плана — БЕЗ новой колонки

Осознанное решение: `plan`-колонки в БД нет. Применение плана пишет per-tenant строки
`FeatureEnablement` (вкл/выкл для каждой функции каталога) и значения `TenantQuota`.
Текущий план **вычисляется обратно** из набора включённых функций
(`plan_code_for_features`). Т.к. план — единственное, что переписывает весь набор
функций сразу, обратное вычисление всегда точное; тенант с ручной правкой честно
читается как «Свой набор» (`plan = null`). Это убрало риск капризной миграции (в репо
тесты миграций чувствительны к смене head).

## Куда пишутся включения функций

`FeatureEnablement` — `TenantBaseModel`, т.е. строки лежат в схеме **самого** тенанта.
`apply_plan` (`backend/app/services/tenants/subscription.py`) открывает сессию,
привязанную к схеме целевого тенанта (`AsyncSessionLocal(tenant=target.slug, …)`, как
`demo_bootstrap` засевает флаги), и пишет явный `on` для каждой функции каталога — `True`
если функция в плане, иначе `False`. Явный `on=False` важен: часть флагов default-on
(`contractors`, `medical`, `warehouse`), и младший тариф обязан их активно выключить.
Квоты (`TenantQuota`, SharedModel) правятся на сессии запроса управляющего тенанта, как
в `patch_fleet_quotas_endpoint`.

## API (`/api/v1/platform/tenants`)

Все за `_require_managing_admin` (токен + роль admin/client_admin/**owner** + запрос под
слагом управляющего тенанта).

- `GET /plans` — каталог планов + каталог функций (для выпадашки во фронте).
- `PATCH /{tenant_id}/plan` `{plan}` — применить тариф; 422 на неизвестный план, 404 на
  неизвестного тенанта. Возвращает `TenantFleetItem` (тенант + квоты + план + функции).
- `GET ""` (список) расширен: у каждого тенанта теперь `plan` (вычисленный) и `features`
  (per-feature `on`/`off`).

Добавлен `owner` в `_MANAGEMENT_ROLES`: фронт даёт `owner` право manage-tenants
(owner = ALL_PERMISSIONS), а бэкенд раньше пускал только admin/client_admin — получалось
«кнопка есть, а сервер 403». Слаг-проверка управляющего тенанта осталась.

## Фронтенд

- `TenantsPage.tsx`: колонка «Тариф» (бейдж текущего плана / «Свой набор») + диалог
  `TenantPlanDialog` — выбор плана с предпросмотром функций и лимитов, «Применить тариф»,

  вызывалось).
- Пункт меню переименован «Управление тенантами» → «Клиенты и подписки» (не путать с
  соседним «Тенанты и роли»).

## Замечания

- Список тенантов читает функции по одной сессии на тенанта — приемлемо для небольших
  флотов; при росте — батч-запрос.
- Планы фиксированы в коде; редактирование наборов/цен из UI — возможное развитие.
