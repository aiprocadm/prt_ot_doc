# Дизайн: Наряд-допуск на высоте (782н) — Ф4 «печатный бланк»

- **Дата:** 2026-06-21
- **Контур:** Наряды-допуски §16, эталон «работа на высоте» (Приказ Минтруда № 782н).
- **Этап:** Ф4 из программы Ф1→Ф4. **Влиты/в PR:** Ф1 (модель+экран, #669), Ф2 (инструктаж+подписи ПЭП, #671), Ф3a (журнал эксплуатации, #673/#674), **Ф3b** (закрытие с подписями, PR #676 открыт). Ф4 — **печатный бланк наряда-допуска** (DOCX, опц. PDF, опц. фирменный бланк). Это завершает эталонный вид работ перед тиражированием на 902н/1479/903н.
- **Полнота стека:** Ф4 — **full-stack** (чистый сборщик DOCX + сервис загрузки/обёртки + API + фронтенд-кнопки). Переиспользует готовый движок печати платформы; новое — только «тело» документа и блок подписей.
- **Ветка:** `feat/work-permits-782n-print`, **стек поверх Ф3b** (`feat/work-permits-782n-closing`, PR #676) — печать рендерит акт закрытия и подписи Ф3b. База PR определяется на финише: `main`, если #676 уже влит; иначе stacked-PR на closing-ветку.
- **Источники:** [Приказ 782н — КонсультантПлюс](https://www.consultant.ru/document/cons_doc_LAW_371453/); движок печати платформы (`domains/templating/renderer.py`, `modules/pdf/`, `modules/branding/letterhead.py`, `modules/headers/engine.py`).

## 1. Контекст и цель

После Ф1-Ф3b наряд-допуск ведётся полностью в системе (форма, инструктаж, подписи, журнал эксплуатации, закрытие с подписями), но **печатного документа нет**: в `api/routes/work_permits.py` нет эндпоинта `print`/`pdf`/`render`. По 782н наряд-допуск — бумажный документ, который должен быть на руках у бригады. Ф4 даёт **печатный бланк**, отражающий текущее состояние наряда, с **блоком подписей ПЭП** (доказательство простой электронной подписи: ФИО + дата + хэш канонического снимка).

**Архитектурное решение:** бланк 782н — фиксированная системная форма «по закону», не пользовательский шаблон. Поэтому строим его **кодом (python-docx)**, а не через admin-загружаемый DOCX-шаблон (Template/TemplateVersion + S3 + seed — избыточная инфраструктура ради одной формы). Конечные стадии (фирменный бланк, DOCX→PDF) переиспользуются из готового конвейера как есть.

## 2. Объём

**В объёме (Ф4):**
- Чистый сборщик `build_work_permit_docx(data) -> bytes` (python-docx) — все секции 782н + блок подписей ПЭП.
- Сервис `render_work_permit(...)` — загрузка наряда+связей+подписей, резолв ФИО, опц. фирменный бланк, опц. конвертация в PDF.
- API `GET /work-permits/{id}/print?format=docx|pdf` (admin, tenant-scoped) → файл.
- Frontend: кнопки «Скачать DOCX»/«Скачать PDF» на карточке наряда.
- Только роль `admin`.

**Вне объёма (следующие этапы):**
- Пиксель-точная типографика официального бланка Росстандарта (цель — полный юридически значимый наряд со всеми данными; уточнение вёрстки — возможный DOCX-шаблон позже).
- Встраивание графических подписей/печатей-изображений (ПЭП подтверждается хэшем, не картинкой).
- Асинхронная генерация через `DocumentPipelineOrchestrator`/Celery (для одного документа синхронно достаточно).
- Тиражирование печати на другие виды работ (902н/1479/903н) — после эталона.
- Сохранение готового файла как `Document`/версии в S3 (печать on-demand, без персистентного артефакта).

## 3. Аудитория и права

- Роль `admin` (специалист по ОТ). Backend `/work-permits` уже гейтит `required_roles=["admin"]`.
- Фронтенд: переиспользуем код `work_permit.view` (печать/скачивание — операция чтения). Новых кодов прав не вводим.
- Tenant-изоляция: печать чужого наряда → 404 (как у прочих эндпоинтов наряда).

## 4. Чистый сборщик документа (backend)

**`backend/app/domains/work_permits/print_form.py`** — без I/O, без sqlalchemy (как `lifecycle.py`):

- Датакласс `WorkPermitPrintData` — снимок для печати: реквизиты наряда (number/work_type/zone/секции 782н/safety_systems/планы/статус/closed_at), `org_header` (название организации/подразделение), `members: list[{role, fio}]`, `briefing: {conducted_by_fio, conducted_at, topics} | None`, `daily_admissions: list[{date, start, end, admitted_by_fio}]`, `extensions: list[{old_end, new_end, at}]`, `completion: {text, recorded_at} | None`, `signatures: list[SignatureLine]`.
- `SignatureLine` = `{group: "permit"|"briefing"|"closing", role_label, fio, status_label, signed_at, mode, hash_short}` (`hash_short` = первые 16 символов `content_hash`).
- `build_work_permit_docx(data: WorkPermitPrintData) -> bytes` — python-docx: формирует документ по секциям (см. §5), возвращает байты. Пустые секции рендерятся как заголовок без строк (типографский бланк их содержит).
- Человекочитаемые метки: vocab ролей/видов работ/систем безопасности/статусов — локальные словари модуля (RU), независимые от фронта (чистый модуль).

`python-docx` доступен (зависимость `docxtpl`); импорт `from docx import Document`.

## 5. Секции бланка (порядок)

1. **Шапка:** организация/подразделение, № наряда, вид работ (метка), статус (метка), план-старт/финиш.
2. **Ответственные и бригада:** таблица «роль (метка) · ФИО».
3. **Описание работ:** зона, содержание, условия, оборудование, опасные факторы, системы безопасности (метки), меры до/в процессе/особые, СИЗ.
4. **Целевой инструктаж:** кто провёл (ФИО), когда, темы (если инструктаж есть).
5. **Ежедневный допуск:** таблица дата/начало/окончание/кто допустил (если есть записи).
6. **Продления:** строки «продлён с X до Y (дата)» из событий `extended.meta` (если есть).
7. **Окончание и закрытие:** акт окончания (`completion_text`), дата оформления, `closed_at`.
8. **Подписи ПЭП:** таблица (§6).

## 6. Блок подписей ПЭП (новое)

Нигде в платформе подписи в печать не встраиваются — строим заново. Источник — таблица `signature_requests` (поля `object_type`, `object_id`, `signer_person_id`, `status`, `content_hash`, `signed_at`, режим из `signature_payload`/`purpose`), три потока наряда: `object_type ∈ {"work_permit", "work_permit_briefing", "work_permit_closing"}`, привязка по `object_id` (id наряда / id инструктажа / id наряда).

Таблица в DOCX, столбцы: **Поток/роль · ФИО · Статус · Дата подписания · Режим · Хэш (ПЭП)**. Группы: подписи наряда (ответственные, Ф2), ознакомление бригады (инструктаж, Ф2), закрытие (сдал/принял, Ф3b). `hash_short` (16 символов `content_hash`) — доказательство ПЭП: бумага несёт отпечаток подписанного содержания. Роль/kind закрытия резолвится из членства (как `signed_closing_kinds`).

## 7. Сервис загрузки и обёртки (backend)

**`backend/app/services/work_permit_print.py`**:

- `render_work_permit(session, *, tenant, permit_id, fmt: "docx"|"pdf", with_letterhead: bool=True) -> RenderedDoc` (`{bytes, filename, media_type}` или доменная ошибка).
- Шаги: (1) загрузить наряд (tenant-scoped, иначе `None`→404 в роуте); (2) загрузить members/briefing/daily_admissions/events(extended)/signatures одним набором запросов; (3) резолв `person_id→ФИО` (как в Ф2 роуте); (4) собрать `WorkPermitPrintData`; (5) `build_work_permit_docx`; (6) если `with_letterhead` и включён `settings.doc_pipeline_letterhead_auto` — `LetterheadResolver(BrandingService(...)).resolve(...)` → `apply_headers_to_docx(...)` (best-effort: при сбое бланка — лог + без бланка, не падаем); (7) если `fmt=="pdf"` — `convert_docx_bytes(...)` через `LibreOfficePool`; при отсутствии `soffice`/таймауте → доменная ошибка `PdfRendererUnavailable` (роут → `503`, понятный код, не 500).
- Имя файла: `work-permit-{number|id}.{docx|pdf}`.

## 8. API (backend, на `routes/work_permits.py`)

- `GET /work-permits/{id}/print?format=docx|pdf` (default `docx`), гейт `admin` (ReaderAccess), `_get_or_404`. Возвращает `Response`/`StreamingResponse` с `Content-Type` (`application/vnd.openxmlformats-officedocument.wordprocessingml.document` / `application/pdf`) и `Content-Disposition: attachment; filename=...`.
- Ошибки: чужой/нет наряда → 404; `format=pdf` при недоступном конвертере → 503 `PDF_RENDERER_UNAVAILABLE` (через `api_problem_detail`); невалидный `format` → 422 (валидация query).

## 10. Обработка ошибок

- Наряд не найден / чужой тенант → 404.
- `format=pdf`, нет LibreOffice/таймаут → 503 `PDF_RENDERER_UNAVAILABLE` + toast на фронте (DOCX остаётся доступен).
- Сбой применения фирменного бланка → лог, документ отдаётся без бланка (best-effort, не 500).
- Пустые секции (нет инструктажа/допусков/закрытия) → секция-заголовок без строк, не ошибка.

## 11. Тестирование

- **Сборщик (`build_work_permit_docx`, unit, без БД):** собрать `WorkPermitPrintData` фикстурой, сгенерировать DOCX, открыть `docx.Document(BytesIO(bytes))`, проверить: № наряда и ФИО членов присутствуют; метки систем безопасности (RU) отрендерены; таблица подписей содержит строку с `hash_short` и ФИО подписанта; пустые секции не роняют сборку.
- **Сервис (`render_work_permit`):** наряд с бригадой+подписями → DOCX-байты непусты, имя файла корректно; `with_letterhead=False` пропускает бланк; PDF-путь — мок/skip если `soffice` нет (`PdfRendererUnavailable` при отсутствии).
- **API:** `GET /print?format=docx` → 200 + правильный `Content-Type`/`Content-Disposition`, тело — валидный DOCX; admin-only (не-admin → 403); cross-tenant → 404; `format=pdf` без конвертера → 503; невалидный format → 422.
- **Frontend:** кнопки рендерятся под `work_permit.view`; клик зовёт api с верным `fmt`.
- Прогон: Py3.12 если доступен, иначе доступный Python с отметкой версии (CLAUDE.md). Frontend: `npm --prefix frontend run test -- <file>` + `build`.

## 12. Критерии приёмки

1. `build_work_permit_docx` — чистый, без I/O; генерирует валидный DOCX со всеми секциями 782н по имеющимся данным.
2. Блок подписей ПЭП печатает три потока (наряд/инструктаж/закрытие) с ФИО+статусом+датой+режимом+хэшем.
3. `GET /print?format=docx` отдаёт DOCX (200, верные заголовки); `format=pdf` — PDF при доступном конвертере, иначе 503 (не 500); admin-only; cross-tenant 404.
4. Фирменный бланк применяется best-effort и не роняет генерацию при сбое.
5. Карточка наряда даёт скачивание DOCX/PDF; PDF-503 → понятный toast.
6. Тесты (сборщик + сервис + API + фронт) зелёные; сборка фронта без ошибок типов/линта.
