# Pilot validation scenarios (phase 1)

Документ фиксирует **пошаговую проверку** ключевых бизнес-сценариев для пилотного клиента. Все шаги построены так, чтобы их мог повторить оператор без доступа к БД.

## Общие предпосылки

- Включены необходимые фичи арендатора через `/api/v1/tenants/{tenantId}/features`.
- Все запросы выполняются с `Authorization: Bearer <token>` и заголовком `X-Tenant: <tenant_slug>`.
- Идемпотентные операции передают `Idempotency-Key`.

### Общие проверки для каждого сценария

- **Аудит**: в `/api/v1/audit` есть запись на каждое критичное действие (создание сущности, смена статуса документа, генерация пакета).
- **Outbox**: события доступны через `/api/v1/admin/outbox?status=FAILED` и `/api/v1/admin/outbox?status=DEAD`.
- **Tasks**: дедлайны и напоминания фиксируются в `/api/v1/tasks` и отправляются через outbox (`TaskDueSoon`, `TaskOverdue`).

## Scenario 1: «Выход на объект»

**Цель**: пройти путь реального клиента — от структуры организации до подписанного комплекта документов и подтверждённых событий.

### 1) Создать организацию и структуру

**API**
1. `POST /api/v1/companies` — создать компанию.
2. `POST /api/v1/sites` — создать объект (привязка к `company_id`).
3. `POST /api/v1/positions` — создать должности для объекта.

**UI**
- Раздел «Компании» → «Создать компанию».
- Раздел «Объекты» → «Создать объект».
- Раздел «Должности» → «Создать должность».

**Проверки**
- Компания/объект/должность отображаются в списках.
- В аудите фиксируются операции создания.

### 2) Добавить сотрудников

**API**
1. `POST /api/v1/persons` — создать сотрудников (с `company_id`, `position_id`).

**UI**
- Раздел «Сотрудники» → «Добавить сотрудника».

**Проверки**
- Сотрудники отображаются в `/api/v1/persons`.
- В аудите — запись о создании сотрудника.

### 3) Назначить обучение / СИЗ / риски

**API**
1. `POST /api/v1/persons/{personId}/trainings` — назначить обучение.
2. `POST /api/v1/ppe/issues` — выдать СИЗ (с `person_id`).
3. `POST /api/v1/risks/registers` — создать реестр рисков (привязать `company_id`/`site_id` если требуется полями).

**UI**
- «Сотрудник» → «Обучение» → «Назначить».
- «СИЗ» → «Выдать».
- «Риски» → «Создать реестр».

**Проверки**
- В `/api/v1/persons/{personId}/trainings` отображается назначение.
- В `/api/v1/ppe/issues` видна выдача.
- В `/api/v1/risks/registers` появляется реестр.
- В задачах появляются дедлайны (обучение/СИЗ при наличии обязательств).

### 4) Сгенерировать пакет документов

**API**
1. `POST /api/v1/templates` — создать шаблон (если не существует).
2. `POST /api/v1/templates/{templateId}/versions` — загрузить версию шаблона.
3. `POST /api/v1/document-packs` — создать пакет документов.
4. `POST /api/v1/document-jobs` — запустить генерацию пакета (с `Idempotency-Key`).
5. `GET /api/v1/document-jobs/{jobId}` — дождаться статуса `completed`.
6. `GET /api/v1/documents?pack_id=<packId>` — получить документы.

**UI**
- «Шаблоны» → «Создать» → «Загрузить версию».
- «Пакеты» → «Создать пакет».
- «Документы» → «Сгенерировать пакет».

**Проверки**
- В `documents` есть записи со статусом `generated`.
- В outbox присутствуют события `DocumentGenerated` и связанные с пакетом.
- В аудите — запись о генерации.

### 5) Подписать / экспортировать

**API**
1. `PATCH /api/v1/documents/{documentId}/status` → `signed`.
2. Повторить с `exported` (или `signed` → `exported`, если разрешено политикой).

**UI**
- «Документ» → «Подписать» → «Экспортировать».

**Проверки**
- Статус документа меняется корректно.
- В outbox появляется `DocumentSigned`/`DocumentExported`.

### 6) Проверить webhooks и дедлайны

**Проверки**
- В `/api/v1/admin/outbox` не остаётся бесконечно `FAILED`/`DEAD` событий.
- Для задач, созданных по обучению, есть `TaskDueSoon`/`TaskOverdue`.
- В `/api/v1/tasks` присутствуют актуальные дедлайны.

## Scenario 2: «Подготовка к проверке»

**Цель**: пройти путь инспекции, закрытия предписаний и экспорта доказательств.

### 1) Создать инспекцию

**API**
1. `POST /api/v1/inspections` — создать инспекцию.
2. `POST /api/v1/inspections/{inspectionId}/violations` — добавить нарушения.
3. `POST /api/v1/violations/{violationId}/corrective-actions` — создать корректирующие действия.

**UI**
- «Инспекции» → «Создать».
- «Нарушения» → «Добавить».
- «Корректирующие действия» → «Создать».

**Проверки**
- Нарушения и корректирующие действия отображаются в списках.
- По корректирующим действиям создаются дедлайны/задачи.

### 2) Сформировать требуемые документы

**API**
1. Использовать `POST /api/v1/document-jobs` для генерации пакета «Проверка».
2. Проверить `GET /api/v1/documents` и `GET /api/v1/documents/{documentId}/versions`.

**UI**
- «Документы» → «Сформировать пакет».

**Проверки**
- Документы сгенерированы, версии доступны.
- В outbox есть событие `DocumentGenerated`.

### 3) Отслеживать дедлайны и закрыть предписания

**API**
1. `GET /api/v1/tasks` — убедиться в дедлайнах.
2. `PATCH /api/v1/inspections/{inspectionId}` — обновить статус инспекции, если предусмотрено бизнес-процессом.

**UI**
- «Задачи» → «Просроченные / Критичные».
- «Инспекции» → «Закрыть».

**Проверки**
- У задач корректно меняются статусы.
- В аудите фиксируется обновление статуса инспекции.

### 4) Экспорт доказательств

**API**
1. Получить документы по инспекции и экспортировать (статус `exported`).

**UI**
- «Документы» → «Экспортировать доказательства».

**Проверки**
- Статус документов `exported`.
- В outbox фиксируется событие `DocumentExported`.

## Scenario 3: «Обучение и обязательства»

**Цель**: подтвердить цикл обучения, протокола/сертификата и работу напоминаний.

### 1) Назначить обучение

**API**
1. `POST /api/v1/persons/{personId}/trainings` — назначить обучение.

**UI**
- «Сотрудник» → «Обучение» → «Назначить».

**Проверки**
- В задачах (`/api/v1/tasks`) появился дедлайн по обучению.
- В outbox появилось событие `TrainingAssigned` (если включено).

### 2) Сгенерировать протокол/сертификат

**API**
1. `POST /api/v1/document-jobs` — запуск пакета с шаблоном «Протокол/Сертификат».
2. `GET /api/v1/document-jobs/{jobId}` — подтвердить завершение.
3. `PATCH /api/v1/documents/{documentId}/status` → `signed`.

**UI**
- «Документы» → «Сгенерировать протокол/сертификат» → «Подписать».

**Проверки**
- Документ сгенерирован и подписан.
- В аудите зафиксированы генерация и подписание.

### 3) Напоминания и просрочки

**API**
1. Убедиться, что запущен `tasks.reminders.dispatch` (celery beat).
2. Проверить `/api/v1/admin/outbox?status=FAILED` и `...status=DEAD`.

**UI**
- «Задачи» → «Скоро срок / Просрочено».

**Проверки**
- Для дедлайна создаётся `TaskDueSoon`, после истечения — `TaskOverdue`.
- В `/api/v1/tasks` видны статусы/сроки.
- Аудит отражает изменения статуса задач.
