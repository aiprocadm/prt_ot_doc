# ADR 0001: Modular Monolith + Schema-per-Tenant

## Статус
Accepted

## Контекст
Платформа объединяет несколько продуктовых контуров (документы, риски, СИЗ/склад, обучение, инциденты/проверки) и должна запускаться просто в Codespaces, но оставаться масштабируемой для enterprise-сценариев.

Нужен компромисс между:
- скоростью разработки и низкой операционной сложностью;
- изоляцией доменной логики и tenant-безопасностью;
- возможностью дальнейшего выделения модулей в отдельные сервисы.

## Решение
1. Выбрать архитектурный стиль **Modular Monolith** с явными bounded contexts.
2. Держать единый runtime/backend, но отделять модули через внутренние контракты (`api/services/repos/schemas/events/tasks`).
3. Multi-tenant стратегию зафиксировать как **schema-per-tenant** для production PostgreSQL, с обязательным `X-Tenant` и tenant context middleware.
4. Межмодульную интеграцию вести через **Outbox events + webhooks**, а не через плотные двусторонние импорты.

## Последствия
### Плюсы
- Быстрый MVP и простой запуск в Codespaces.
- Чёткие границы между доменами, снижение связанности.
- Понятный путь к эволюции в service-based архитектуру.

### Минусы
- Требуется дисциплина контрактов и контроль импортов.
- Нужна строгая observability/аудит трассировка в рамках одного runtime.
- Для SQLite dockerless режимов часть production-механик (напр. `search_path`) реализуется как функциональный эквивалент.

## Alternatives considered
- **Микросервисы с первого дня**: отклонено из-за высокой операционной цены для MVP и onboarding.
- **Классический неструктурированный монолит**: отклонено из-за рисков неконтролируемой связанности и сложной эволюции.
