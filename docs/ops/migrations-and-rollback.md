# Migrations and rollback plan (phase 2)

Документ фиксирует проверку миграций, шаги отката и правила soft-/hard-delete для пилотного запуска.

## 1) Валидация миграций

### Пустая БД

1. Создайте пустую базу данных.
2. Запустите миграции:
   ```bash
   PYTHONPATH=backend python -m alembic -c backend/app/migrations/alembic.ini upgrade heads
   ```
3. Убедитесь, что сервис стартует и `/health` отвечает `200`.

### Миграция с предыдущей версии

1. Определите текущую ревизию (например, через `alembic current`).
2. Поднимите среду со старым кодом и схемой.
3. Выполните upgrade до `head` по той же команде.
4. Проверьте, что ключевые сценарии из `docs/pilot/scenarios.md` проходят без регрессий.

## 2) Политика отката (rollback)

### Общий алгоритм

1. Остановить входящий трафик (LB/ingress).
2. Снять бэкап БД **до** downgrade.
3. Откатить миграции:
   ```bash
   PYTHONPATH=backend python -m alembic -c backend/app/migrations/alembic.ini downgrade -1
   ```
4. Вернуть предыдущий релиз приложения.
5. Прогнать smoke-тесты (login, list documents, list tasks).

### Какие миграции требуют особой осторожности

Следующие миграции содержат изменения данных/DDL, которые могут быть **невосстанавливаемыми** без бэкапа:

- Изменения enum-типов (например, `documentstatus`, `roleenum`).
- Миграции с `op.execute(...)` и массовыми `UPDATE` (например, изменения outbox и данных пакетов).
- Миграции, удаляющие столбцы/таблицы (при downgrade данные будут потеряны).

**Рекомендация:** хранить точку восстановления БД перед каждым релизом, а rollback выполнять только вместе с резервной копией.

## 3) Soft-delete vs hard-delete

| Сущность | Политика | Где проверять |
| --- | --- | --- |
| Документы | **Нет удаления**, используется статус (`archived/revoked`) | `/api/v1/documents/{id}/status` |
| Шаблоны | **Hard-delete**, но запрещено удалять используемые | `/api/v1/templates/{template_id}` |
| Пакеты документов | **Soft-delete** (`deleted_at`) через архивирование | `/api/v1/document-packs/{packId}` |
| Компании/объекты/сотрудники | **Soft-delete** (`deleted_at`) через archive/deactivate | `/api/v1/companies`, `/api/v1/sites`, `/api/v1/persons` |
| Задачи/обязательства | Нет удаления API, только смена статуса | `/api/v1/tasks` |

## 4) Контрольные вопросы перед пилотом

- Есть ли свежий бэкап БД перед выкладкой?
- Протестирован ли `upgrade` с пустой БД и с прошлой версией?
- Подтверждён ли rollback на тестовой среде?
