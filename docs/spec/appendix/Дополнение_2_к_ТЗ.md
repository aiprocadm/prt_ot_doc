# 59. Простота интерфейса: измеримый UX-бюджет экрана

В базовом ТЗ (разд. 8) и vNext (§4) уже есть принципы: progressive disclosure, «не более 7–9 колонок», safe UX. Но это декларации, которые нельзя проверить на приёмке. Чтобы интерфейс действительно был простым для обычного пользователя, нужны измеримые лимиты (UX-бюджет) и чек-лист, по которому дизайнер и разработчик проверяют каждый экран перед сдачей.

## 59.1 Принцип «одного экрана — одна задача»

Каждый экран отвечает на один вопрос пользователя и ведёт к одному основному действию. Если экран пытается решать две разные задачи — его нужно разделить или увести второе в отдельный шаг/вкладку.

- У экрана есть одна главная цель, сформулированная словами («выдать СИЗ сотруднику», «проверить готовность объекта»).
- На экране один основной CTA (primary), визуально доминирующий. Остальные действия — вторичны и приглушены.
- Всё, что не помогает главной цели прямо сейчас, скрыто под «Дополнительно», вкладками или отдельным экраном.

## 59.2 UX-бюджет: жёсткие числовые лимиты

Лимиты «по умолчанию» на любой основной рабочий экран. Превышение допустимо только с явным обоснованием и пометкой в ревью.

| Параметр экрана | Лимит по умолчанию | Что делать при превышении |
| --- | --- | --- |
| Основных действий (primary CTA) | 1 (максимум 2) | Оставить одно; остальные — в secondary/меню |
| Видимых полей в форме (без «Дополнительно») | ≤ 7 | Лишнее — под «Дополнительно» / шаги мастера |
| Колонок в таблице по умолчанию | ≤ 7 | Остальные — в настройке колонок / карточке строки |
| Шагов мастера на экране | 1 шаг = 1 экран | Многошаговый мастер вместо длинной формы |
| Уровней вложенности навигации до цели | ≤ 3 | Плоская структура + поиск/командная строка |
| Блоков информации (карточек/секций) на дашборде | ≤ 6 | Приоритизировать; лишнее — на второй экран |
| Разных цветов статусов в одной таблице | ≤ 5 | Свести к семантическим (ок/внимание/ошибка/нейтр.) |
| Одновременных модальных окон | 1 | Никаких модалок поверх модалок |

## 59.3 Три уровня раскрытия сложности

Каждый сложный экран проектируется в три слоя. Обычный пользователь живёт на уровне 1 и почти никогда не спускается ниже.

| Уровень | Кто видит | Что содержит |
| --- | --- | --- |
| 1. Основной | Все, по умолчанию | Главная цель, 1 CTA, минимум обязательных полей, понятный статус. |
| 2. Дополнительно | Кто нажал «Дополнительно» | Необязательные поля, тонкие настройки, редкие опции. |
| 3. Экспертный | Power-user / админ | Массовые операции, ручные переопределения, служебные данные, конфигурация. |

> Правило по умолчанию Пользователь должен уметь выполнить типовой сценарий, не открывая уровень 2 и 3 вообще. Если для базовой задачи приходится лезть в «Дополнительно» — значит, поле стоит не на том уровне. «Простой по умолчанию, мощный по требованию».

# 60. Чек-лист приёмки экрана (UX Definition of Done)

Экран нельзя считать готовым, пока не пройден этот чек-лист. Он дополняет критерии приёмки разд. 47 базового ТЗ и применяется к каждому пользовательскому экрану. Формулировки — проверяемые «да/нет».

## 60.1 Ясность и фокус

☐ Понятно с первого взгляда, для чего этот экран и что здесь главное действие.

☐ Один доминирующий primary CTA; вторичные действия визуально слабее.

☐ Соблюдён UX-бюджет разд. 59.2 (поля ≤7, колонки ≤7, блоки ≤6 и т.д.) — или есть обоснование.

☐ Нет технического жаргона в подписях, видимых обычному пользователю (термины — человеческим языком).

## 60.2 Прогрессивное раскрытие

☐ Типовой сценарий выполняется без открытия «Дополнительно».

☐ Необязательные и редкие поля скрыты (уровень 2/3 по разд. 59.3).

☐ Служебные/технические данные отделены от бизнес-контента.

## 60.3 Понятность и подсказки

☐ Пустое состояние (empty state) объясняет, что делать дальше (создать/импортировать/мастер), а не просто «нет данных».

☐ У нетривиальных полей есть микроподсказка или пример заполнения.

☐ Ошибки написаны понятно: что не так и как исправить (не код и не stack trace).

☐ Статусы единообразны с остальной системой (те же слова, те же цвета).

## 60.4 Безопасность действий (Safe UX)

☐ Опасные действия (удаление, массовые операции, отправка) требуют подтверждения.

☐ Есть автосохранение или предупреждение о несохранённых изменениях.

☐ Массовые операции показывают preview/dry-run и прогресс; есть откат, если поддерживается.

☐ Длинные операции не блокируют интерфейс; виден прогресс.

## 60.5 Единообразие и доступность

☐ Карточка сущности следует единому паттерну (summary → tabs → timeline → действия).

☐ Кнопки, таблицы, фильтры, бейджи — из общей design-system, а не «свои».

☐ Экран корректно работает по правам: пользователь не видит действий, которых ему нельзя (permission-aware UI).

☐ Экран пригоден для мобильного/сенсорного использования, если сценарий полевой.

## 60.6 Тест «нового пользователя»

Финальная проверка: человек, впервые открывший экран, выполняет основную задачу без внешней помощи и без обучения. Если он «застрял», спрашивает «а что тут делать», или ошибся с первого раза — экран не прошёл приёмку.

> Как это встроить в процесс Чек-лист 60.1–60.6 — обязательная часть Definition of Done для любого экрана (в т.ч. в PR-шаблоне). В product analytics (разд. 35 базового ТЗ) отслеживать: незавершённые мастера, частые ошибки, точки отказа — это объективный сигнал перегруженного экрана. Периодические usability-тесты на реальных пользователях каждой роли (разд. 43.5 базового ТЗ).

# 61. Модульная поставка: только нужные модули заказчику

Ваш запрос: давать конкретному заказчику не весь функционал, а только необходимые модули. В коде уже есть механика per-tenant feature-флагов (feature_flags.py, FeatureEnablement), но у неё два ограничения: она default-on (всё включено, пока явно не выключишь) и покрывает лишь ~8 фич из тарифов. Для управляемой модульной поставки нужна полноценная модель entitlements («что заказчику продано → то он и видит»).

## 61.1 Каталог модулей (Module Registry)

Единый реестр всех функциональных модулей платформы — источник истины для того, что вообще можно включать/выключать. Каждый модуль описывается:

| Атрибут модуля | Назначение |
| --- | --- |
| code | Машинный код (напр. training, ppe, edo, ecology, fire_safety, bdd). |
| title / описание | Человеческое название для админ-консоли и коммерческого предложения. |
| category | Дисциплина/группа (ОТ, ПБ, ПромБез, Экология, ГО-ЧС, БДД, документы, ядро). |
| depends_on | От каких модулей зависит (нельзя включить обучение без ядра сотрудников). |
| is_core | Ядро — нельзя выключить (tenancy, auth, документы, аудит). |
| editions | В какие редакции входит по умолчанию (Start/Business/Suite/Enterprise). |
| ui_routes | Какие экраны/маршруты фронтенда принадлежат модулю (для скрытия навигации). |
| permissions | Какие права относятся к модулю (для связки с RBAC). |

## 61.2 Entitlement: что включено у конкретного заказчика

Для каждого tenant хранится набор включённых модулей (entitlements) — результат того, что заказчику продали/выдали. Ключевые отличия от текущих флагов:

- Default-OFF для некорневых модулей: по умолчанию заказчик видит только ядро + модули своей редакции. Остальное — выключено, пока не выдано явно. Это обратная логика к нынешней default-on.
- Три источника включения: (а) редакция тарифа даёт базовый набор; (б) индивидуальные надбавки («докупленный модуль»); (в) временный доступ (trial модуля на N дней).
- Проверка зависимостей: нельзя выдать модуль без его depends_on; система предложит включить зависимости или запретит.
- Безопасное выключение: отключение модуля не удаляет данные — они переходят в read-only/скрываются; при повторном включении всё возвращается.

## 61.3 Три уровня фильтрации (сквозной enforcement)

Модульный доступ должен соблюдаться на всех слоях, а не только прятать пункт меню. Иначе заказчик, знающий URL, достучится до выключенного модуля.

| Слой | Что делает | Результат для выключенного модуля |
| --- | --- | --- |
| Frontend (навигация) | Скрывает пункты меню, дашборд-виджеты, действия выключенных модулей. | Пользователь их просто не видит. |
| Frontend (роутинг) | Блокирует прямой переход по URL выключенного модуля. | Редирект на «модуль недоступен» / 404. |
| Backend (API-guard) | Каждый роут модуля проверяет entitlement до бизнес-логики. | HTTP 404/403 «module_not_enabled». |

Это расширение уже существующего в коде module-level access (vNext-SEC-01, test_rbac_module_access.py): к проверке роли добавляется проверка «включён ли модуль у tenant» — и она идёт первой.

## 61.4 Связка «модули × редакции × роли»

Три независимых измерения доступа, которые нельзя путать:

| Измерение | Вопрос | Механизм |
| --- | --- | --- |
| Модуль (entitlement) | Куплен ли модуль этим ЗАКАЗЧИКОМ? | Module Registry + Entitlements (разд. 61) |
| Редакция (тариф) | Какой набор модулей даёт тариф? | subscription/plans (уже в коде) |
| Роль (RBAC/ABAC) | Может ли этот ПОЛЬЗОВАТЕЛЬ внутри заказчика? | rbac_abac (уже в коде) |

> Порядок проверки доступа (важно) Правильная последовательность при каждом запросе: 1) есть ли tenant-контекст → 2) включён ли модуль у заказчика (entitlement) → 3) есть ли у роли право (RBAC/ABAC) → 4) доступен ли конкретный объект (ABAC). Модуль проверяется раньше роли: незачем проверять права на то, чего у заказчика вообще нет.

## 61.5 Управление из админ-консоли

- Экран «Модули заказчика»: список всех модулей с переключателями вкл/выкл, видно — что от редакции, что докуплено, что в trial.
- Применение редакции одним действием (как уже делает plans.py): выбрал «Business OT» → включился нужный набор модулей и квоты.
- Пресеты модулей под отрасль: «стройка», «производство», «транспорт» — быстрый старт нужного набора (связка со starter-packs из Дополнения №1, разд. 52.3).
- Аудит изменений: кто, когда, какой модуль включил/выключил у заказчика (feature governance, разд. 37 базового ТЗ).
