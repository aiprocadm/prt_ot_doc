# 71. Миграция и импорт данных как продукт

Слово «миграция» в базовом ТЗ встречается 0 раз, «импорт» — 4 раза поверхностно. Но каждый новый клиент, reseller и арендатор приходит с горой данных в Excel, Word, 1С и старых системах. Если затащить их тяжело — сделка срывается. Для вашей аутсорсинговой модели (много клиентов) это не удобство, а условие работы.

## 71.1 Импорт-фреймворк (единый механизм)

Не разрозненные импортёры под каждую сущность (как сейчас только СОУТ), а один фреймворк, переиспользуемый везде:

| Возможность | Требование |
| --- | --- |
| Форматы | XLSX, CSV, JSON; шаблоны загрузки под каждую сущность (скачать пустой шаблон с нужными колонками). |
| Маппинг полей | Визуальный маппинг «колонка файла → поле системы»; автоопределение по заголовкам; сохранение схемы маппинга для повтора. |
| Валидация до записи | Проверка типов, обязательных полей, справочников, дубликатов, связей — с понятным отчётом об ошибках построчно. |
| Dry-run (сухой прогон) | Показать, что будет создано/обновлено/пропущено, БЕЗ записи в БД — как в replace engine. |
| Частичный импорт | Импортировать корректные строки, отложить ошибочные в «на исправление», не падать целиком. |
| Откат импорта | Отменить импортированную партию целиком (по import batch id), если что-то пошло не так. |
| Идемпотентность | Повторный импорт того же файла не создаёт дубли (по ключу сущности). |
| Прогресс | Асинхронный импорт больших файлов с прогрессом и отчётом (как pipeline). |

## 71.2 Миграция с типовых источников

Готовые сценарии переезда снижают барьер входа — это прямой инструмент продаж:

- Из Excel/Word (типовой случай) — мастера под частые структуры: штатное расписание, списки сотрудников, журналы, нормы СИЗ.
- Из 1С — через коннектор (заявлен в ТЗ разд. 33) или выгрузку: оргструктура, кадры.
- С конкурентов (КОТ, 1С:EHS, Courson и др., упомянуты в vNext §1.1) — импорт-профили под их форматы выгрузки, где возможно. Это буквально «переманивание клиентов».
- Между режимами внутри платформы: миграция клиента Lightweight → Dedicated (Доп. №1, разд. 49) без потери истории — это тоже миграция данных.

## 71.3 Качество данных при импорте

Импорт — главный источник грязных данных. Связка с Data Quality Layer (базовый ТЗ разд. 15):

- Импортированные данные сразу проходят проверки Data Quality; проблемные — помечаются, а не тихо принимаются.
- Маппинг на справочники: незнакомые значения (должность, которой нет в справочнике) — предложить создать или сопоставить, а не молча пропустить.
- Отчёт об импорте: сколько создано/обновлено/пропущено/с ошибками, скачиваемый, с привязкой к batch id для отката.

> Продуктовый эффект Хороший импорт — это сокращение time-to-value с недель до часов. Для аутсорсера, заводящего десятки клиентов, разница между «ручной ввод каждого» и «загрузил Excel — получил готовый контур» определяет, сколько клиентов вы физически потянете. Это не техническая деталь, а множитель вашей ёмкости.

# 72. Жизненный цикл клиента: онбординг → офбординг

Онбординг в ТЗ есть (разд. 38). Но офбординга нет вообще — что происходит, когда клиент уходит, как он забирает данные, что удаляется. Это и юридическое требование (152-ФЗ, право на данные — Доп. №3 разд. 66), и вопрос доверия: корпоративный закупщик спрашивает «как мы заберём данные, если решим уйти?» раньше, чем «какие у вас функции».

## 72.1 Полный жизненный цикл (карта состояний)

| Стадия | Что происходит | Статус в ТЗ |
| --- | --- | --- |
| Trial / demo | Пробный доступ, sandbox, demo-данные | Есть (разд. 38) |
| Онбординг | Создание аренды, импорт, настройка, старт | Есть (разд. 38) + импорт (разд. 71) |
| Активная работа | Штатное использование | Есть (весь ТЗ) |
| Приостановка | Неоплата / пауза → safe read-only, данные сохранены | Частично (биллинг разд. 36) |
| Офбординг | Уход клиента: экспорт данных, передача, удаление | ОТСУТСТВУЕТ |
| Пост-офбординг | Retention-период, окончательное удаление, аудит | ОТСУТСТВУЕТ |

## 72.2 Офбординг: экспорт и возврат данных

Право клиента забрать СВОИ данные в пригодном виде. Это антидот к страху vendor lock-in и требование 152-ФЗ.

- Полный экспорт данных арендатора: все сущности клиента (сотрудники, документы, риски, обучение, СИЗ, история) в машиночитаемом виде (JSON/XLSX) + файлы (PDF/DOCX) архивом.
- Отличие от export_center: тот выгружает отчёты/KPI; здесь — ПОЛНЫЙ дамп данных арендатора для переезда. Это новая функция.
- Структурированный формат: не «свалка», а понятная структура со схемой, пригодная для импорта в другую систему (симметрия с разд. 71).
- Самообслуживание: владелец аренды может инициировать экспорт сам, не через поддержку (для аренды); для аутсорсинга — аутсорсер по запросу клиента.
- Аудит экспорта: кто, когда, какой объём выгрузил (ПДн — чувствительная операция).

## 72.3 Офбординг: удаление и retention

После ухода — управляемое удаление, а не «данные висят вечно» или «удалили сразу и потеряли».

- Grace-период: после расторжения данные хранятся N дней (read-only) на случай возврата или споров — конфигурируемо.
- Окончательное удаление: по истечении — полное удаление данных арендатора (включая файлы в S3, бэкапы по политике) с актом/подтверждением.
- Юридические исключения: что закон требует хранить дольше (некоторые документы ОТ имеют сроки хранения) — не удалять слепо.
- Обезличивание вместо удаления, где нужно сохранить статистику без ПДн.
- Каскад по иерархии: уход reseller'а (Доп. №1) — что с его клиентами? Явная процедура, а не сирота-данные.

> Почему это продаёт Парадокс: наличие лёгкого выхода повышает готовность войти. Заказчик, который видит «мы в любой момент заберём данные одной кнопкой», доверяет больше, чем тот, кому выход не показали. Отсутствие офбординга читается как «нас хотят запереть» — и убивает корпоративные сделки на этапе due diligence.

# 73. Версионирование и совместимость API

API уже под /v1 (аудит подтвердил), но политики версионирования нет. Пока потребитель API один (ваш фронт) — не проблема. Но вы планируете публичный API, интеграции и reseller'ов НА вашей платформе. Как только появится хоть один внешний потребитель — ломать контракты станет нельзя. Это дёшево заложить сейчас и очень дорого вводить потом.

## 73.1 Политика версионирования

- Версия в пути (/api/v1/, /api/v2/) — уже так; закрепить как правило.
- Semantic versioning контрактов: ломающие изменения → новая мажорная версия; добавления (новые поля/эндпоинты) → в текущей.
- Что считается ломающим: удаление/переименование поля, изменение типа, изменение семантики, ужесточение валидации. Явный список в ТЗ.
- Что НЕ ломающее: добавление необязательного поля, нового эндпоинта, нового значения enum (при толерантном клиенте).

## 73.2 Deprecation (управляемое устаревание)

Нельзя просто выключить старую версию — на ней живут интеграции клиентов и reseller'ов.

| Этап | Что делается |
| --- | --- |
| Анонс | Объявление устаревания версии/эндпоинта заранее (напр. за 6–12 мес), в changelog и через заголовок Deprecation. |
| Параллельная работа | Старая и новая версии работают одновременно весь период миграции. |
| Предупреждения | Ответы старой версии содержат Deprecation/Sunset заголовки; уведомления потребителям API. |
| Мониторинг использования | Видно, кто ещё на старой версии, чтобы не отключить используемое. |
| Отключение | Только после того, как трафик старой версии упал до нуля / истёк объявленный срок. |

## 73.3 Контрактная стабильность (уже частично есть)

- OpenAPI как контракт — в базовом ТЗ заявлен; закрепить: любое изменение API отражается в OpenAPI и проходит contract-тесты (в репо есть test_openapi_contract.py).
- Contract-тесты в CI: ломающее изменение без смены версии — красный билд.
- Версионирование вебхуков и их payload'ов (не только REST) — событие тоже контракт.
- Идемпотентность и optimistic concurrency (заявлены в ТЗ) — часть стабильного контракта для машинных потребителей.

# 74. Эксплуатация: деплой без простоя и откат

В ТЗ есть observability (разд. 41) и бэкапы (разд. 44), а откат миграций даже задокументирован в коде. Но нет главного для арендной модели: как выкатывать обновления без простоя. Для SaaS, который вы сдаёте в аренду, простой = недовольные заказчики и нарушенный SLA. Canary упомянут в ТЗ 1 раз — этого мало.

## 74.1 Стратегия деплоя без простоя

- Zero-downtime deployment: обновление без остановки сервиса (rolling / blue-green). Пользователи не видят «идут технические работы».
- Canary / поэтапный выкат: новая версия сначала на часть трафика/арендаторов, при проблемах — стоп до массового раската.
- Feature flags для релиза (механизм уже есть в коде): выкатить код выключенным, включить постепенно, при проблеме — выключить без отката деплоя.
- Health-gated rollout: раскат продолжается только если health-checks (уже есть) зелёные.

## 74.2 Миграции БД на живой системе (критично для мультиарендности)

Самое опасное: миграция схемы на живых данных многих арендаторов. Откат задокументирован, но нужны правила безопасности миграций как требование ТЗ.

- Только additive-миграции по умолчанию (уже правило разд. 36 vNext): добавление, не удаление — чтобы старый и новый код работали на одной схеме во время раската.
- Expand-contract паттерн: сначала добавить новое (expand), выкатить код, потом удалить старое отдельным шагом (contract) — а не всё сразу.
- Миграция по всем схемам арендаторов: schema-per-tenant означает N схем; миграция должна безопасно и отслеживаемо пройти по всем, с прогрессом и возможностью паузы.
- Обратная совместимость на время раската: во время деплоя одновременно работают старый и новый код — схема должна поддерживать оба.
- Тест миграций (в репо мощно покрыт — test_migrations_comprehensive_safety.py): закрепить как обязательный gate.

## 74.3 Откат и аварийное восстановление

- Быстрый откат релиза: возможность вернуть предыдущую версию за минуты (процедура есть — закрепить SLA отката).
- Разделение отката кода и данных: откатить код можно быстро; откат миграции данных — по документированной процедуре (ROLLBACK_PLAN.md) с бэкапом до downgrade.
- Runbook инцидентов: что делать при сбое деплоя, зависшей миграции, деградации (частично есть в docs/ops/failure-scenarios.md — довести до полноты).
- RTO/RPO (в ТЗ заявлены: RTO ≤4ч, RPO ≤24ч) — связать с процедурами деплоя/отката.

## 74.4 Среды и продвижение изменений

- Явные среды: dev → staging → production, с данными разного уровня (staging — обезличенные/тестовые).
- Продвижение через среды: изменение проходит staging до прода; на staging — прогон миграций и e2e.
- Конфигурация по средам (уже есть CONFIGURATION_MATRIX.md, settings_staging_hardening) — закрепить в ТЗ.

# 75. Приёмка и интеграция в код

Критерии приёмки (дополняют разд. 47 базового ТЗ) + патчи и промпт по схеме предыдущих дополнений.

## 75.1 Критерии приёмки

### Миграция/импорт (разд. 71)

- Импорт XLSX с маппингом полей и dry-run работает; ошибочные строки не роняют импорт целиком; откат партии по batch id доступен.
- Импортированные данные проходят Data Quality; отчёт об импорте скачивается.

### Жизненный цикл (разд. 72)

- Полный экспорт данных арендатора (не только отчётов) в машиночитаемом виде + файлы; операция в аудите.
- Офбординг: grace-период → удаление с подтверждением; юр. исключения по срокам хранения учтены; каскад по reseller определён.

### API (разд. 73)

- Политика версий зафиксирована; ломающее изменение без смены версии = красный contract-тест.
- Deprecation: заголовки Deprecation/Sunset + мониторинг использования старой версии.

### Эксплуатация (разд. 74)

- Zero-downtime деплой подтверждён; миграция проходит по всем схемам арендаторов с прогрессом; откат за минуты по процедуре.
