ИНСТРУКЦИЯ ПО ВНЕДРЕНИЮ

Как влить все дополнения в код

Единый порядок действий для Дополнений №1–№4 (разделы 49–74) через Claude Code

> Это практическое руководство, а не ещё одно ТЗ. У вас четыре дополнения, в каждом свой промпт. Запускать их вразнобой — рискованно (конфликты правок, нарушенный порядок). Здесь — один выверенный порядок: подготовка, единый мастер-промпт для вливания требований в канон, проверка, и затем — очередь реализации по фазам. Всё в терминах вашего репозитория prt_ot_doc.

> Ключевой принцип Есть разница между «влить требования в канон» (чтобы «продолжай по ТЗ» их видел) и «реализовать код». Первое — быстро и безопасно, делается один раз мастер-промптом. Второе — долго, делается фазами. Сначала канон, потом реализация по одной фазе. Не пытайтесь реализовать всё сразу.

# 4. Очередь реализации после вливания

Требования в каноне — дальше реализация по фазам. Порядок не случаен: сначала чиним фундамент (безопасность), потом строим ценность для вашего бизнеса, потом расширяем. Каждую фазу запускаете отдельно фразой «продолжай по ТЗ, Phase N».

| Очередь | Фаза | Что реализуется | Почему в этом порядке |
| --- | --- | --- | --- |
| 1-я | 16 | Security hardening: RLS, impersonation-контроль, SAST-gate | Фундамент. XXE уже пофикшен в мастер-промпте; RLS — второй рубеж изоляции ДО наращивания функций. |
| 2-я | 11 | Managed Clients + UX-бюджет + entitlements | Ядро вашей ценности как аутсорсера + основа модульных продаж. Опора: packs, contractors, feature_flags. |
| 3-я | 17 | Import framework | Множитель ёмкости: без импорта не завести клиентов массово. Опора: sout_import. |
| 4-я | 12 | Change Feed + Compliance Baseline | Подписная модель сопровождения. Опора: rules_engine, data_quality. |
| 5-я | 13–14 | White-label + reseller + self-service аренда | Тиражирование: продажа и аренда. Опора: branding, subscription. |
| 6-я | 18–19 | Offboarding + API governance | Доверие (выход данных) + защита интеграций. Нужны до масштабных продаж. |
| 7-я | 15, 20 | Дисциплины + zero-downtime ops | Расширение охвата и зрелость эксплуатации. Каждая дисциплина — отдельный инкремент. |

> Почему безопасность первой, а не бизнес-функции Соблазн — начать с Managed Clients (это же деньги). Но строить многоклиентский контур на единственном рубеже изоляции (Доп. №3 разд. 65) — значит множить поверхность утечки между клиентами. RLS дешевле внедрить на 40 таблицах сейчас, чем на 120 через полгода. Фундамент → этажи, не наоборот.

# 5. Частые проблемы и как их избежать

| Риск | Как избежать |
| --- | --- |
| Claude Code пытается реализовать всё сразу | В промпте явно: «только заведение требований в канон, без реализации доменов». Реализация — отдельными фазами. |
| Правки затирают существующее | Требование additive в промпте + git diff перед коммитом; ревью, что только добавления. |
| Конфликт с уже существующими разделами канона | Мастер-промпт сначала ЧИТАЕТ файлы (структуру), потом вставляет — не вслепую. |
| RLS-миграция ломает живую систему | Phase 16: сначала показать план миграции и список таблиц, дождаться подтверждения; expand-contract. |
| Забыли про XXE, реализуя новое | XXE-фикс — Часть 0 мастер-промпта, ДО всего остального. Приоритет №1. |
| Дополнения-docx устарели после правок кода | Источник истины после вливания — канон в репо; docx в appendix/ — исторический исходник. |

## 5.1 Мини-чеклист перед стартом реализации каждой фазы

- Прочитать соответствующий раздел дополнения (что именно требуется).
- Проверить в матрице покрытия текущий статус REQ-ID.
- Проверить, на какие существующие модули опирается фаза (колонка «Опора» в разд. 4).
- Соблюдать «шесть вопросов» + седьмой (security) из product_spec.py.
- После фазы — обновить матрицу (статус → done/partial) и handoff в AI_IMPLEMENTATION_REPORT.md.
Коротко

Порядок один: (1) ветка → (2) положить дополнения в репо → (3) мастер-промпт вливает требования в канон + чинит XXE → (4) проверить, что «продолжай по ТЗ» видит новое → (5) реализовывать по фазам, начиная с безопасности (Phase 16), потом Managed Clients (Phase 11), потом импорт (Phase 17), и далее по таблице. Требования в канон вливаются один раз и быстро; реализация — по одной фазе, не всё сразу. После вливания источник истины — репозиторий, а не docx.
