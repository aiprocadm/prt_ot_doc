# 49. Контур Managed Clients (ведение клиентов аутсорсером)

Это — главный отсутствующий слой. Сейчас ТЗ и код оперируют понятием tenant (арендатор). В коде уже есть managing tenant (управляющая аренда с fleet-менеджментом) и поле parent_id у арендатора — но это техническая инфраструктура, а не бизнес-модель ведения клиента. Нужно ввести доменную сущность, отражающую то, как аутсорсер реально работает.

## 49.1 Ключевая сущность: ManagedClient

Ввести сущность ManagedClient — «клиент, которого ведёт аутсорсинговая компания». Это не то же самое, что арендатор: у одного аутсорсера-арендатора может быть десятки managed-клиентов внутри его собственного tenant-пространства.

- Модель ведения — два поддерживаемых режима:
- Lightweight (внутри tenant аутсорсера) — клиент существует как организация (Company/Group) внутри рабочего пространства аутсорсера. Быстро, дёшево, подходит для разовых работ и малых клиентов.
- Dedicated (отдельный tenant клиента) — под клиента поднимается собственный изолированный tenant, а аутсорсер получает к нему делегированный доступ. Для крупных клиентов, которым позже можно передать «ключи» (аренда — см. разд. 53).
- Обязательное требование: переход клиента из Lightweight в Dedicated без потери истории (миграция данных клиента в новый tenant с сохранением timeline, документов, аудита).

## 49.2 Единое окно аутсорсера (Client Cockpit)

Отдельный рабочий стол роли «Аутсорсер / руководитель проектов», показывающий все ведомые клиенты сразу:

| Блок | Что показывает |
| --- | --- |
| Портфель клиентов | Список всех managed-клиентов: статус договора, режим (Lightweight/Dedicated), readiness, число открытых задач, ближайшие дедлайны. |
| Cross-client Attention | Сводный «Центр внимания» по ВСЕМ клиентам: где просрочки, где не готов допуск, у кого истекает обучение/медосмотр/СИЗ, где висит согласование. |
| Cross-client календарь | Единый календарь дедлайнов по всем клиентам с фильтром по клиенту/специалисту/типу. |
| Загрузка специалистов | Сколько клиентов/задач на каждом специалисте ОТ/ПБ/эколога; выявление перегруза. |
| Быстрый старт сценария | Запуск разового комплекта (разд. 50) для любого клиента в 2–3 клика прямо из окна. |
| Рентабельность (связь с CRM) | По каждому клиенту: договор, трудозатраты, статус оплат (интеграция с CRM/billing-контуром). |

## 49.3 Делегированный доступ и «работа от имени клиента»

- Специалист аутсорсера должен переключаться между клиентами без перелогина (client switcher, аналог tenant switcher, но внутри портфеля).
- Impersonation / «работа в контексте клиента» — с обязательной пометкой в аудите: кто, от имени какого клиента, что сделал. Требование ПДн: действия аутсорсера в данных клиента всегда трассируемы.
- Матрица прав аутсорсер → клиент: какие специалисты аутсорсера к каким клиентам и модулям допущены (ABAC-атрибут managed_client_id).
- Клиент (если у него есть кабинет) не видит других клиентов аутсорсера и не видит внутренней кухни — только свой контур (разд. 25 базового ТЗ + разд. 51).

> Почему это критично Без слоя Managed Clients платформа заставит аутсорсера заводить под каждого клиента отдельную «инсталляцию» и прыгать между ними. Это убивает главную ценность аутсорсинга — эффект масштаба на портфеле. Единое окно + cross-client attention — это то, что превращает платформу из «редактора документов» в «операционную систему аутсорсера».

# 50. Сценарные разовые комплекты документов

Ваш явный запрос: «быстро подготовить разовый комплект документов для заказчика по разным сценариям». В базовом ТЗ пакеты (разд. 46) и Scenario Presets (разд. 24) есть, но описаны как побочная функция. Для аутсорсера это — основной ежедневный сценарий заработка, и он должен быть первоклассным.

## 50.1 Библиотека сценариев (Scenario Catalog)

Каталог готовых сценариев, каждый — это шаблонизированный «рецепт» комплекта. Минимальный набор для запуска:

| Сценарий | Что генерирует комплект (ядро) | Дисциплина |
| --- | --- | --- |
| Выход на объект / допуск бригады | Приказы, допуски, инструкции по должностям, перечни СИЗ, наряды-допуски, чек-лист готовности | ОТ + ПромБез |
| Несчастный случай | Извещения, приказ о комиссии, протоколы опроса, акт Н-1, план мероприятий, отчётность | ОТ |
| Подготовка к проверке (ГИТ/МЧС/Роспотреб/РТН) | Gap-analysis, сбор пакета, генерация недостающих форм, экспортный комплект | Любая (по типу надзора) |
| Новый подрядчик | Анкета, проверка готовности, договорной пакет, допуск, инструктажи | ОТ + ПромБез |
| Приём нового сотрудника | Вводный/первичный инструктаж, направление на медосмотр, карточка СИЗ, ознакомления | ОТ |
| Пожарная проверка объекта | Приказы, инструкции ПБ, планы эвакуации, журналы, программа тренировки | ПБ |
| Экологический пакет (постановка объекта) | Инвентаризация источников, паспорта отходов, расчёты, календарь отчётности | Экология |
| Пакет ГО и ЧС | План ГО, приказы, составы комиссий, программа учений, журналы | ГО и ЧС |

## 50.2 Мастер разового комплекта (Quick Pack Wizard)

От выбора сценария до готового ZIP/PDF — не более 4 шагов:

- Выбор сценария и клиента — из каталога (50.1) и портфеля (разд. 49). Система подтягивает всё, что уже знает о клиенте.
- Догрузка недостающих данных — мастер спрашивает ТОЛЬКО то, чего не хватает (объект, состав бригады, должности, даты). Progressive disclosure + guided data collection.
- Предпросмотр состава и readiness — что войдёт в комплект, Document Readiness Score, чего не хватает и почему, какие формы будут сгенерированы.
- Генерация и выдача — pipeline генерирует DOCX→PDF→ZIP; результат можно скачать, отправить в ЭДО или в кабинет клиента; всё логируется в timeline клиента.

> Требования, отличающие «разовый» режим Работа без долгой настройки клиента — разовый комплект можно собрать для «клиента-однодневки», заведённого за минуту (минимальный обязательный набор полей). Шаблонные наборы данных клиента — переиспользуемые «профили клиента» (реквизиты, оргструктура, типовые должности), чтобы не вводить одно и то же. Сохранение своих сценариев — аутсорсер создаёт собственные сценарии-пресеты (свой набор шаблонов + правила именования + маршрут), в т.ч. отраслевые. Пакетная генерация на много сотрудников/объектов — один сценарий → комплект на 50 человек одним запуском (Batch, разд. 11 базового ТЗ).

# 51. Долгосрочное сопровождение: отслеживание изменений у клиента

Ваш второй запрос по цели №1: при долгосрочном сотрудничестве отслеживать все изменения в компании заказчика и готовить необходимые документы. Это превращает разовую услугу в подписную модель сопровождения — и требует change-driven автоматики.

## 51.1 Client Change Feed (лента изменений клиента)

По каждому managed-клиенту — единая лента отслеживаемых изменений, каждое из которых может порождать обязательства:

| Тип изменения у клиента | Что система должна предложить/сделать автоматически |
| --- | --- |
| Принят новый сотрудник | Задача: вводный/первичный инструктаж, направление на медосмотр, карточка и выдача СИЗ, ознакомление с инструкциями. |
| Уволен / переведён сотрудник | Закрытие карточек, возврат СИЗ, отзыв допусков, актуализация журналов. |
| Новая должность / рабочее место | Пересчёт норм СИЗ, требований по обучению, оценка рисков, набор обязательных инструкций. |
| Новый объект / площадка | Проверка обязательного пакета по объекту, назначение ответственных, пакет допуска. |
| Изменение оргструктуры | Пересчёт назначений, ответственных, маршрутов согласования. |
| Изменение вида деятельности / оборудования | Пересмотр рисков, СОУТ-обязательств, ПромБез/ОПО, пожарных требований. |
| Наступление срока (обучение/медосмотр/СИЗ/проверка) | Автозадача на продление + генерация комплекта заранее (за N дней). |
| Изменение НПА | Impact-analysis: какие документы клиента устарели, задачи на актуализацию (разд. 14 базового ТЗ). |

## 51.2 Источники сигналов об изменениях

- Ручной ввод специалистом аутсорсера или самим клиентом через упрощённый кабинет (разд. 25).
- Импорт кадровых изменений — периодическая загрузка штатки/оргструктуры (CSV/XLSX/1С-коннектор) с diff «что изменилось с прошлого раза».
- Data Quality Layer — выявляет неполноту/просрочку, которая тоже есть «изменение состояния» (разд. 15 базового ТЗ).
- Rules engine — правила «если у клиента X, то создать задачу/комплект Y» (разд. 16 базового ТЗ).

## 51.3 Профиль сопровождения клиента (Compliance Baseline)

Для каждого долгосрочного клиента — «эталон соответствия»: что у него должно быть (по его отрасли, объектам, должностям, применимым НПА). Система непрерывно сравнивает факт с эталоном и показывает разрыв.

- Client Readiness Dashboard — «светофор» по клиенту: ОТ / ПБ / ПромБез / Экология / ГО-ЧС / БДД, где зелёное/жёлтое/красное с расшифровкой.
- Периодический авто-аудит — регулярная сверка (напр. еженедельно) с формированием отчёта «что изменилось, что просрочено, что нужно сделать».
- Отчёт клиенту — авто-генерируемый периодический отчёт о состоянии соответствия (ценность подписки, обоснование абонплаты).

> Продуктовый эффект Change Feed + Compliance Baseline — это механизм, который делает долгосрочный контракт самоокупаемым: система сама подсказывает специалисту, что нужно сделать у клиента, генерирует комплект и формирует отчёт. Аутсорсер продаёт не «разовые документы», а непрерывное поддержание соответствия.

Тиражирование: продажа другим аутсорсерам и аренда заказчикам

# 52. Продажа платформы другим аутсорсинговым компаниям

Ваша цель №2. В vNext-spec есть «Outsource OT Edition», white-label и reseller-кабинет (§3, §23.4), но это перечислено одной строкой. Чтобы платформу реально можно было сдать другому аутсорсеру, нужна проработанная модель тиражирования, изоляции и брендирования.

## 52.1 Иерархия арендаторов и роль Reseller

Три уровня, опирающиеся на уже существующие в коде managing tenant и parent_id:

| Уровень | Кто это | Что может |
| --- | --- | --- |
| Platform Owner | Вы — владелец платформы | Создаёт reseller'ов, задаёт редакции/тарифы, глобальные шаблоны-эталоны, биллинг верхнего уровня, feature governance. |
| Reseller (аутсорсер-партнёр) | Другая аутсорсинговая компания, купившая платформу | Ведёт СВОИХ клиентов (Managed Clients, разд. 49), под своим брендом, со своими шаблонами; получает свой reseller-кабинет и суб-биллинг. |
| Managed Client / Tenant | Клиент reseller'а или ваш клиент | Работает в своём изолированном контуре; может со временем «выкупить» аренду (разд. 53). |

- Reseller НЕ видит клиентов других reseller'ов и данные Platform Owner. Жёсткая изоляция на всех уровнях иерархии (расширение tenant isolation, разд. 3 базового ТЗ).
- Каскадное отключение: приостановка reseller'а безопасно приостанавливает его клиентов (safe read-only), но не удаляет данные.

## 52.2 White-label (полное перебрендирование)

Существующий модуль branding покрывает бренд документов. Для продажи платформы нужен white-label всего приложения:

- Логотип, название, цветовая тема, favicon, домен/поддомен reseller'а.
- Кастомизация писем, уведомлений, PDF-колонтитулов, кабинета клиента под бренд reseller'а.
- Скрытие любых упоминаний исходного вендора (при соответствующей лицензии).
- Свои юридические тексты (оферта, политика ПДн, согласия) на уровне reseller'а.

## 52.3 Тиражирование настроек (Configuration Templating)

Главная техническая ценность для продажи — возможность развернуть нового reseller'а/клиента «из коробки» с преднастроенным содержимым, а не с пустой системой.

- Эталонные наборы («starter packs»): библиотека шаблонов документов, справочники (должности, вредные факторы, опасности, нормы СИЗ), методики рисков, сценарии, маршруты, правила — как переносимые пакеты.
- Экспорт/импорт конфигурации tenant'а: выгрузить настройку эталонного клиента и развернуть её у нового (без бизнес-данных, только конфигурация).
- Отраслевые пресеты: «строительство», «производство», «транспорт», «энергетика» — с преднастроенными шаблонами и правилами под отрасль.
- Версионирование эталонов и управляемое обновление: Platform Owner обновил эталонный шаблон → reseller'ам предлагается принять обновление (без затирания их правок).

## 52.4 Reseller-кабинет и суб-биллинг

- Отдельный кабинет reseller'а: его клиенты, потребление, его собственные лимиты, его выручка по клиентам.
- Двухуровневый биллинг: Platform Owner тарифицирует reseller'а (напр., по числу клиентов/сотрудников/генераций), reseller тарифицирует своих клиентов по своей модели.
- Usage metering на каждом уровне (расширение разд. 36 базового ТЗ): активные сотрудники, генерации, ЭДО, storage — с агрегацией вверх по иерархии.

# 53. Аренда платформы крупным и мелким заказчикам

Ваша цель №3. Отличие от продажи аутсорсеру (разд. 52): заказчик сам ведёт свою охрану труда на арендованной платформе, а не ведёт чужих клиентов. Это классический SaaS-self-service, но с продуманной «вилкой» от мелкого клиента до холдинга.

## 53.1 Редакции под размер заказчика

Опираемся на редакции vNext (§3), но привязываем к явным профилям заказчика и уже реализованным в коде тарифам free / pro / enterprise:

| Профиль заказчика | Редакция | Ядро функций |
| --- | --- | --- |
| Микро/малый (1 юрлицо, до ~50 чел.) | Start OT | Документы, инструктажи, карточки СИЗ, базовые риски, кабинет, уведомления. Self-service онбординг. |
| Средний (несколько объектов) | Business OT | + Обучение, медосмотры, склад СИЗ, проверки, НПА, дашборды, календарь. |
| Крупный / многопрофильный | Safety Suite | + Полный контур ОТ/ПБ/ПромБез/Экология, workflow-конструктор, rules engine, аналитика. |
| Холдинг с филиалами | Enterprise Holding | + Группа компаний, SSO/LDAP, deep-интеграции, on-prem/private cloud, расширенная изоляция, приоритетный SLA. |

## 53.2 Self-service аренда (для мелких/средних)

- Регистрация и создание tenant — самостоятельно, с trial/demo (разд. 38 базового ТЗ уже описывает onboarding и sandbox).
- Мастер запуска («Готовность к запуску») — компания, объекты, импорт сотрудников, выбор отрасли и пресетов, роли, бренд, старт задач.
- Выбор редакции и оплата — прозрачные тарифы, ROI-калькулятор, автопродление, grace period, safe read-only при неоплате.
- Работа с преднастроенным содержимым — не пустая система, а отраслевой starter-pack (разд. 52.3).

## 53.3 Enterprise-аренда (для крупных/холдингов)

- Индивидуальный онбординг с сопровождением (может выполнять сам аутсорсер как услугу — связка с разд. 49).
- Изоляция уровня database-per-tenant / private cloud / on-prem (уже предусмотрено в разд. 3 базового ТЗ для on-premise).
- SSO/SAML/LDAP, deep-интеграции (1С, HR, BI/DWH), выделенный SLA, DPA/договор на обработку ПДн.
- Группа компаний / филиальная иерархия внутри одного enterprise-tenant.

## 53.4 Гибридная модель: аутсорсер + аренда (ключевой сценарий)

Самый ценный для вас сценарий — плавный переход клиента по мере роста доверия:

| Этап отношений | Модель | Кто работает в системе |
| --- | --- | --- |
| Разовая услуга | Managed Client (Lightweight, разд. 49) | Только аутсорсер |
| Долгосрочное сопровождение | Managed Client (Dedicated) + Change Feed | Аутсорсер ведёт, клиент подгружает данные через кабинет |
| Совместная работа | Аренда (co-managed) | Клиент работает сам + аутсорсер имеет делегированный доступ и контроль |
| Полная самостоятельность | Аренда (self-service) | Клиент работает сам, аутсорсер — по запросу / консалтинг |

> Требование к переходам Все переходы между моделями — без потери данных и без пересоздания: история, документы, timeline, аудит сохраняются. «Передача ключей» клиенту (из Managed в аренду) — это управляемая операция с перевыпуском прав, а не экспорт-импорт вручную. Именно эта бесшовность — ваше конкурентное преимущество: вы можете начать с разовой продажи и дорастить клиента до подписки на аренду, оставаясь его подрядчиком.

# 54. Пожарная и промышленная безопасность

## 54.1 Пожарная безопасность (ПБ)

Реализовать функционал специалиста по ПБ. В коде уже есть fire-safety, fire-inspections, fire-training — расширить до полного контура:

- Объекты защиты: реестр зданий/помещений, категории по пожарной опасности, системы противопожарной защиты (АУПС/АУПТ/СОУЭ), первичные средства пожаротушения (учёт, сроки перезарядки/поверки).
- Документы ПБ: приказы, инструкции о мерах ПБ (общеобъектовые и по помещениям), планы эвакуации, регламенты, декларация ПБ, журналы.
- Противопожарные инструктажи и ПТМ: вводный/первичный/повторный/внеплановый/целевой, пожарно-технический минимум, журналы, контроль сроков.
- Тренировки и учения: план-график тренировок по эвакуации, протоколы, анализ.
- Регламентные работы и проверки: ТО систем ПБ, испытания (напр., пожарные лестницы, водопровод), чек-листы, предписания, устранение.
- Аналитика ПБ: состояние объектов, просрочки ТО/перезарядки, готовность к проверке МЧС.

## 54.2 Промышленная безопасность (ПромБез)

Функционал специалиста по ПромБез для организаций, эксплуатирующих ОПО:

- Реестр ОПО: идентификация, класс опасности, регистрационные сведения, карты объектов, технические устройства.
- Технические устройства и оборудование: учёт, экспертиза промышленной безопасности (ЭПБ), сроки, диагностика, история работ.
- Производственный контроль: план ПК, мероприятия, ответственные, отчётность в надзор.
- Аттестация по промбезопасности персонала (области аттестации), сроки, связь с обучением.
- Связи с нарядами-допусками (уже есть work-permits), рисками, оборудованием, расследованиями инцидентов на ОПО.
- Документы и отчётность: ПЛА (план ликвидации аварий), положения, приказы, отчёты для Ростехнадзора.

# 55. Экологическая безопасность

Функционал эколога предприятия. Расширение vNext §20.3 до рабочего контура:

## 55.1 Учётные объекты и источники

- Объекты НВОС (негативного воздействия на окружающую среду): категория объекта (I–IV), постановка на учёт, актуализация сведений.
- Источники загрязнения: стационарные источники выбросов, инвентаризация, ПДВ/НДВ.

## 55.2 Отходы, выбросы, вода

- Выбросы: инвентаризация, нормативы, производственный экологический контроль (ПЭК), план-график замеров.
- Водопользование: водопотребление/водоотведение, разрешения, учёт.

## 55.3 Расчёты, платежи, отчётность

- Расчёт платы за НВОС: по выбросам/сбросам/отходам, авансовые платежи, декларация о плате.
- Экологическая отчётность: 2-ТП (отходы/воздух/водхоз), отчёт по ПЭК, отчётность по объектам НВОС — как формы документной фабрики.
- Экологический календарь: сроки сдачи отчётности, платежей, замеров, продления разрешений — в общий календарь и Attention Center.

# 56. Гражданская оборона, ЧС и безопасность дорожного движения

## 56.1 ГО и ЧС

Функционал специалиста по ГО и ЧС. Расширение vNext §20.4:

- Документы и отчётность: приказы, положения, инструкции, отчётность в органы управления ГОЧС.

## 56.2 Безопасность дорожного движения (БДД)

- Водители: водительский состав, стаж/категории, режим труда и отдыха, нарушения.

# 57. Сквозная связность и «замена специалиста»

Чтобы платформа не превратилась в набор разрозненных модулей по каждой дисциплине, критично реализовать сквозные связи и общую автоматику. Именно это отличает «набор реестров» от «системы, заменяющей специалиста».

## 57.1 Мультидисциплинарная карточка объекта и сотрудника

- Карточка объекта 360°: на одном экране — обязательства и статус по ВСЕМ применимым дисциплинам (ОТ/ПБ/ПромБез/Экология/ГО-ЧС/БДД), а не отдельные экраны на каждую.
- Карточка сотрудника 360°: все его обучения, допуски, медосмотры, СИЗ, аттестации по всем дисциплинам сразу.

## 57.2 Единый Attention Center по всем дисциплинам

«Центр внимания» (разд. 23 базового ТЗ) агрегирует просрочки и риски по всем контурам: истёк инструктаж по ПБ, просрочена ЭПБ на ОПО, приближается срок сдачи 2-ТП, просрочен техосмотр ТС, не проведены учения по ГО — всё в одном месте, с приоритизацией.

## 57.3 Rules engine как «мозг специалиста»

Именно правила (разд. 16 базового ТЗ) реализуют экспертные знания каждой дисциплины и обеспечивают автоматизацию:

- «Если объект категории I по НВОС → требуется ПЭК, декларация НВОС, паспорта отходов» — автозадачи и обязательные документы.
- «Если эксплуатируется ОПО → нужна аттестация по промбезопасности, производственный контроль, ПЛА».
- «Если есть транспорт → предрейсовые медосмотры, техконтроль, ответственный за БДД».
- Библиотека предустановленных правил по каждой дисциплине (поставляется как starter-pack, разд. 52.3) — это и есть «зашитая экспертиза», заменяющая ручной анализ специалиста.

## 57.4 Дисциплинарные дашборды и отчёты руководителю

- Отдельные операционные дашборды по каждой дисциплине + сводный «директорский» дашборд по всей безопасности предприятия.
- Авто-отчёты о состоянии по каждой дисциплине (для клиента при аренде / для заказчика при аутсорсинге).

> Важная оговорка про «замену специалиста» Платформа автоматизирует рутину и снимает нагрузку — генерацию документов, контроль сроков, напоминания, сбор пакетов, проверку полноты. Но экспертные и юридически значимые решения (оценка конкретного риска, подписание акта, ответственность за ОПО) остаются за аттестованным специалистом. Правильная формулировка цели — платформа как «цифровой помощник, многократно ускоряющий специалиста и покрывающий 80% рутины», а не как замена аттестации и ответственности. Это стоит зафиксировать в ТЗ, чтобы избежать завышенных ожиданий и юридических рисков при продаже.

# 58. Критерии приёмки по новым разделам

Дополняют разд. 47 базового ТЗ. Формулировки — machine-checkable, пригодны для матрицы покрытия TZ_COVERAGE_MATRIX.md.

## 58.1 Аутсорсинговый контур (разд. 49–51)

- Один пользователь-аутсорсер видит портфель из ≥2 клиентов в едином окне; cross-client Attention Center агрегирует просрочки по всем клиентам.
- Разовый комплект по сценарию генерируется за ≤4 шага мастера; результат (ZIP/PDF) сохраняется в timeline клиента.
- Client Change Feed: добавление сотрудника у клиента автоматически создаёт корректный набор задач (инструктаж/медосмотр/СИЗ).
- Действия аутсорсера «от имени клиента» полностью трассируются в аудите (кто, от имени кого, что).
- Переход клиента Lightweight → Dedicated сохраняет всю историю и документы.

## 58.2 Продажа и аренда (разд. 52–53)

- Reseller ведёт своих клиентов под своим брендом и НЕ имеет доступа к данным других reseller'ов (подтверждено тестами изоляции).
- White-label: новый reseller получает приложение со своим логотипом/темой/доменом без правок кода.
- Новый tenant разворачивается из отраслевого starter-pack с преднастроенными шаблонами/справочниками/правилами (не пустым).
- Двухуровневый биллинг: потребление клиента агрегируется к reseller'у, потребление reseller'а — к Platform Owner.
- Self-service аренда: заказчик самостоятельно регистрируется, проходит мастер запуска, выбирает редакцию; при неоплате — safe read-only без потери данных.
- Переход Managed → Аренда («передача ключей») выполняется как управляемая операция без пересоздания и потери данных.

## 58.3 Мультидисциплинарность (разд. 54–57)

- Каждая дисциплина (ПБ, ПромБез, Экология, ГО-ЧС, БДД) переиспользует общее ядро (объекты, документы, обучение, проверки, задачи, аудит) — без дублирующих подсистем.
- Дисциплины включаются/выключаются feature-флагами по редакции/клиенту.
- Карточка объекта 360° показывает статус по всем применимым дисциплинам на одном экране.
- Единый Attention Center агрегирует дедлайны минимум из 3 разных дисциплин.
- Для каждой дисциплины есть библиотека предустановленных правил (starter-pack) и минимум один готовый сценарный комплект (разд. 50).
