# ЕДИНОЕ УЛУЧШЕННОЕ ТЗ ПЛАТФОРМЫ vNext

## SaaS / Enterprise платформа по ОТ, ПБ, ПромБез, Экологии, обучению, ЭДО, рискам, СИЗ, проверкам, инцидентам и обязательным процессам

---

## 0. Статус документа и правило для доработки существующего проекта

### 0.1 Назначение документа

Этот документ является **upgrade-spec** для существующей платформы. Его задача — не снести уже сделанное, а:

* сохранить работающий функционал;
* выровнять продукт относительно конкурентов;
* добавить недостающие модули и сценарии;
* усилить UX, мобильность, аналитику и стабильность;
* зафиксировать архитектурные правила, чтобы новые функции можно было добавлять без деградации системы.

### 0.2 Базовое правило развития

Любая дальнейшая разработка должна идти по принципу:

* **не ломать существующие рабочие сценарии**;
* добавлять функциональность **через расширение модулей, feature flags, backward-compatible API и миграции**;
* не допускать хаотичного роста сущностей, экранов и интеграций;
* каждую новую функцию проектировать сразу в трех плоскостях:

  1. бизнес-ценность;
  2. UX-реализуемость;
  3. эксплуатационная надежность.

### 0.3 Стратегическая цель продукта

Платформа должна стать:

* цифровым ядром процессов ОТ/ПБ/ПромБез/Экологии;
* единым реестром обязательств, событий, документов и сроков;
* платформой для холдингов, филиалов, подрядчиков и клиентов;
* системой, которая одинаково хорошо работает для специалиста ОТ, руководителя, преподавателя, кадровика, кладовщика, подрядчика и клиента;
* продаваемым SaaS-продуктом с понятной упаковкой, быстрой демонстрацией ценности и возможностью enterprise-внедрения.

## 1. Целевой конкурентный уровень и продуктовая цель

### 1.1 Платформа обязана закрывать конкурентный паритет по следующим направлениям

#### Паритет с KOT

Нужно не хуже:

* обучение;
* медосмотры;
* СОУТ;
* происшествия и микротравмы;
* проверки и аудиты с мобильного;
* СИЗ;
* промбез;
* электронная подпись;
* риски;
* подрядчики;
* комитеты;
* техника и оборудование;
* богатая статистика;
* календарь;
* интеграции с HR/ERP/API.

#### Паритет с 1С:EHS

Нужно не хуже:

* enterprise-масштабирование;
* холдинговая структура;
* OT + PB + ПромБез + Экология + ГО/ЧС + транспортная безопасность + электробезопасность;
* наряды-допуски;
* отчетность;
* сложные корпоративные роли;
* интеграции с 1С-контуром;
* большой объем печатных форм и регламентной отчетности;
* поддержка тяжелых сценариев и крупных внедрений.

#### Паритет с Courson

Нужно не хуже:

* автоматизация внутреннего обучения;
* кабинет предприятия;
* кабинет слушателя;
* назначения на массовую аудиторию;
* протоколы и журналы;
* электронное подписание обучения;
* уведомления по обучению;
* дистанционная модель обучения и подтверждения прохождения.

#### Паритет с OTOR

Нужно не хуже:

* простота интерфейса;
* быстрый старт;
* облачная модель без тяжелого внедрения;
* умный календарь;
* несколько организаций в одном кабинете;
* понятные роли;
* бюджетный контур;
* шаблоны документов;
* простое освоение системы.

#### Паритет с UMS

Нужно не хуже:

* терминальный режим;
* kiosk/проходной контур;
* идентификация по бейджу/штрихкоду/NFC/биометрии;
* инструктажи для сотрудников, гостей и подрядчиков;
* быстрые предсменные проверки;
* экранная подпись/ЭЦП;
* фото- и видеоподтверждение;
* интеграция со СКУД.

#### Паритет с RiskProf

Нужно не хуже:

* глубокий модуль оценки профрисков;
* база опасностей и мер;
* загрузка штатного расписания;
* связка СОУТ + ОПР + СИЗ;
* автоматическая генерация инструкций;
* перечни медосмотров;
* нормы СИЗ;
* редактируемые выходные документы;
* сильный учебный контур в части тестов и методического обновления.

### 1.2 Платформа должна быть сильнее конкурентов в пяти направлениях

1. **Логика интерфейса и понятность сценариев**
2. **Скорость освоения и минимизация ручных действий**
3. **Единая архитектура расширения модулей**
4. **Стабильность, self-healing и эксплуатационная предсказуемость**
5. **Мобильная и field-ready работа, а не просто “responsive web”**

## 2. Продуктовые принципы платформы

### 2.1 Главный принцип

Платформа должна давать пользователю **не набор реестров**, а **результат по рабочему сценарию**.

### 2.2 Обязательные продуктовые принципы

1. **Task-first и scenario-first**: пользователь работает через “что сделать”, а не только через “в какой модуль зайти”.
2. **Role-based workspace**: у каждой роли свой стартовый экран, свои KPI и свои быстрые действия.
3. **Progressive disclosure**: сложность раскрывается по мере необходимости.
4. **Zero-duplicate-entry**: если данные уже есть в системе или интеграции, пользователь не вводит их повторно.
5. **Safe-by-default UX**: черновики, автосохранение, preview, dry-run, rollback, предупреждение об ошибке.
6. **One truth, many views**: одна сущность — много представлений, но без дублирования данных.
7. **Mobile as real work surface**: мобильная версия должна решать реальные задачи “в поле”.
8. **Self-healing operations**: платформа должна уметь переживать сбои внешних систем и долгие операции.
9. **Modular growth**: новые функции должны подключаться без переделки ядра.
10. **Sellability by design**: демо, trial, onboarding, упаковка тарифов, white-label и ROI должны быть заложены в продукт.

## 3. Издания продукта и упаковка для продажи

### 3.1 Продукт должен поддерживать несколько изданий

Чтобы платформа действительно продавалась, нужно не одно “монолитное предложение”, а продуктовые редакции:

* **Start OT** — базовая SaaS-версия для небольших компаний;
* **Business OT** — документы, обучение, медосмотры, СИЗ, риски, проверки;
* **Safety Suite** — полный контур ОТ/ПБ/ПромБез/Экология;
* **Enterprise Holding** — холдинговая версия с deep integrations, SSO, on-prem/private cloud;
* **Training Center Edition** — акцент на обучение, кабинеты предприятия/слушателя, массовые назначения, протоколы, удостоверения;
* **Outsource OT Edition** — для аутсорсинговых компаний, ведущих несколько клиентов;
* **Contractor Portal Pack** — подрядчики, допуск, внешний контур;
* **Field & Terminal Pack** — мобильный полевой контур, kiosk, biometric/SCUD;
* **AI Copilot Pack** — интеллектуальные подсказки и помощник;
* **Industrial Extensions Pack** — ГО/ЧС, транспортная безопасность, электробезопасность, видеоналитика, экологический контур.

### 3.2 Коммерческая упаковка

Платформа должна поддерживать:

* прозрачные тарифы для SMB;
* индивидуальные условия для enterprise;
* бесплатный trial / demo tenant;
* ROI-калькулятор;
* пакетное лицензирование по модулям;
* биллинг по активным сотрудникам и фактическому использованию;
* white-label для партнеров;
* reseller/partner-кабинет.

## 4. Информационная архитектура и логика пользовательского интерфейса

## 4.1 Два режима входа в работу

Пользователь должен иметь:

### Модульная навигация

* Компании и объекты;
* Сотрудники;
* Документы;
* Обучение;
* Инструктажи;
* Медосмотры;
* СОУТ;
* Риски;
* СИЗ;
* Склад;
* Инциденты;
* Проверки;
* Предписания;
* Подрядчики;
* НПА;
* Аналитика;
* Администрирование.

### Сценарная навигация

* оформить выход на объект;
* допустить подрядчика;
* назначить обучение;
* провести инструктаж;
* выдать СИЗ;
* подготовиться к проверке;
* зарегистрировать инцидент;
* расследовать НС;
* закрыть предписание;
* обновить документы по НПА;
* запустить пакет документов;
* отправить документы в ЭДО;
* проверить просрочки по сотрудникам/объектам;
* подготовить пакет по филиалу;
* открыть новую компанию/новый объект.

## 4.2 Role-based workspaces

Для каждой роли нужен отдельный workspace:

* владелец аренды;
* администратор;
* специалист ОТ;
* руководитель ОТ;
* инженер ПБ;
* специалист по промбез;
* эколог;
* кадровик;
* кладовщик/СИЗ;
* методист;
* преподаватель;
* слушатель;
* аудитор;
* клиент;
* подрядчик;
* руководитель объекта.

Каждый workspace должен содержать:

* ключевые KPI;
* просрочки;
* задачи на сегодня;
* быстрые действия;
* рекомендации;
* последние события;
* календарь;
* незавершенные черновики;
* статус интеграций, если он важен для роли.

## 4.3 Command Center / Центр внимания

Нужен единый операционный экран, где видны:

* критические просрочки;
* зависшие согласования;
* проблемные документы;
* ошибки интеграций;
* high-risk объекты;
* незакрытые предписания;
* истекающие обучения, медосмотры, СИЗ;
* офлайн-конфликты мобильных клиентов;
* задачи без исполнителя;
* tenant health warnings.

## 4.4 Smart calendar

Календарь должен стать одной из сильнейших функций платформы и быть лучше, чем у конкурентов, особенно учитывая замечания пользователей к OTOR.

Календарь обязан:

* собирать события из всех модулей в одно место;
* показывать несколько типов событий одновременно;
* иметь day/week/month/year views;
* поддерживать saved filters;
* показывать план/факт;
* визуализировать загрузку исполнителей;
* показывать просрочки и SLA;
* строить аналитику по типам событий;
* уметь экспортироваться в Outlook/Google/ICS;
* уметь пушить события во внешние календари;
* поддерживать зависимые события и повторяемые задачи;
* учитывать бюджеты/ресурсы, где применимо.

## 4.5 Universal search + command bar

Нужны:

* глобальный поиск по сущностям, метаданным и содержимому документов;
* универсальная command bar для быстрого перехода, поиска, создания сущностей и запуска действий;
* recent items;
* saved searches;
* быстрые команды вида “создать акт”, “назначить инструктаж”, “найти сотрудника”, “проверить допуск подрядчика”.

Структура карточки:

* summary header;

* tabs;
* timeline;
* связанные сущности;
* файлы;
* задачи;
* комментарии;
* аудит;
* быстрые действия.

## 4.7 Реестры

Все реестры должны поддерживать:

* фильтрацию;
* серверную пагинацию;
* сортировку;

## 4.8 Безопасный UX

Обязательно:

* черновики;

* preview перед применением;

Карточка сотрудника должна быть одним из центров платформы и включать:

## 5.4 Data Quality Layer

Платформа обязана иметь слой контроля качества данных:

* обязательные поля;
* логические конфликты;
* дубликаты;

* общую полноту tenant;

* блокирующие ошибки;
* список объектов/сотрудников/подрядчиков, которые нельзя использовать в ключевых сценариях.

* шаблон;
* версия шаблона;
* макет;
* replace map;
* pipeline profile;
* document instance;
* document version;
* approvals;
* signatures;
* archive;
* external delivery.

## 6.2 Template Engine

Поддержать:

* DOCX templating;
* placeholders, conditions, loops;
* вложенные таблицы;
* вычисляемые поля;
* форматирование дат/чисел;
* склонения;
* fallback values;
* branded templates;
* variable inspector;
* test render;
* sample dataset.

## 6.3 Header/Footer Engine

Поддержать:

* первая/четные/нечетные страницы;

## 6.4 Replace Engine

Поддержать:

* body/tables/headers/footers/textboxes;
* case-sensitive;
* whole-word;
* regex;
* dry-run;
* diff preview;
* rollback;

Требования:

Документ/пакет должен иметь score готовности, который учитывает:

* полноту данных;
* обязательные вложения;
* обязательные подписи;
* актуальность НПА;

* готовность к PDF;
* готовность к согласованию;
* готовность к ЭДО;
* готовность к архиву.

Для шаблонов, документов и пакетов обязателен compare mode:

## 35. Критерии приемки по ключевым блокам

### 35.1 UX и сценарии

* новый пользователь своей роли может выполнить базовый сценарий без внешнего обучения;

* есть safe preview/dry-run для массовых действий;
* workspace действительно отличается по ролям.

### 35.2 Документы

* generate с одинаковым Idempotency-Key возвращает один бизнес-результат;
* PDF корректен;
* readiness score объясняет неготовность;
* diff версий работает;
* replace rollback работает.

### 35.3 Обучение

* массовые назначения работают на large batch;
* есть кабинет предприятия и кабинет слушателя;
* протоколы и подписи работают;
* уведомления по отстающим и просроченным работают.

### 35.4 Медосмотры / СОУТ / Риски

* СОУТ влияет на медосмотры, СИЗ и риски;
* риск-движок умеет строить результат из штатки + СОУТ + настроек;

### 35.5 СИЗ и склад

* личные карточки корректны;
* есть остатки, партии, закупки, прогнозы;
* выдача с мобильного работает;
* бюджетный блок не конфликтует со складским учетом.

### 35.6 Инциденты / проверки

* есть фото/видео evidence;
* offline field capture работает;
* CAPA влияет на статусы и аналитику;
* checklist + акт + предписание формируются автоматически.

### 35.7 Подрядчики и допуск

* внешний контур простой и пошаговый;
* readiness допуска показывает причины блокировки;

### 35.8 Надежность

* watchdog ловит зависшие jobs;

## 36. Что обязательно дать Codex/Claude вместе с этим ТЗ

Чтобы AI действительно дорабатывал платформу правильно, вместе с этим ТЗ ему нужно передавать следующие ограничения:

### 36.1 Архитектурные ограничения

* не ломать существующие рабочие модули;
* не удалять действующие API без слоя совместимости;
* все новые функции добавлять через feature flags;
* использовать additive DB migrations;
* сохранять tenant isolation;
* не смешивать доменные контексты напрямую;
* тяжелые операции выносить в async workers.

### 36.2 Инженерные требования

* писать unit/integration/e2e tests;
* покрывать новые доменные инварианты;
* документировать новые endpoints;
* вести changelog;
* обновлять OpenAPI;
* добавлять seed/demo data;
* создавать migration scripts;
* логировать correlation-id;
* соблюдать строгую типизацию на backend и frontend.

### 36.3 Product/UX требования

* не добавлять новый экран без определения primary user goal;
* не добавлять новую сущность без связи с existing master data;
* не создавать новый workflow, если его можно выразить через rules/presets/tasks;
* не перегружать формы;
* все массовые операции — только с preview и прогрессом;
* все mobile/field функции — только с учетом offline.

### 36.4 Критически важное правило

Любая новая функция должна сопровождаться ответом на 6 вопросов:

1. Для какой роли она нужна?
2. В каком сценарии она используется?
3. Какие данные ей нужны и откуда они берутся?
4. Как она ведет себя при отсутствии сети/ошибке интеграции?
5. Как пользователь понимает, что произошло и что делать дальше?
6. Как она отключается/включается по tenant без глобального refactor?
