# FRONTEND_GAP_ANALYSIS

## 1) Что уже было в репозитории

По состоянию на аудит фронтенд уже содержал системный каркас SaaS-приложения:

- единый роутер с защищёнными маршрутами (`ProtectedRoute`) и отдельной страницей отказа в доступе;
- role/permission-модель с RBAC + ABAC проверками;
- tenant-aware API-клиент с обязательным заголовком `X-Tenant-ID` для бизнес-запросов;
- обязательные разделы навигации (дашборды, документы, шаблоны, генерация, пайплайны/jobs, архив/поиск, ЭДО, риски, СИЗ, склад, обучение, инциденты, проверки, CRM/финансы, отчёты, интеграции, админка, клиентский портал);
- набор общих UI-примитивов (таблицы, фильтры, пустые/ошибочные/загрузочные состояния, permission-gates).

## 2) Чего не хватало (выявлено в рамках текущего прохода)

- обязательная документация `docs/FRONTEND_*` была частично устаревшей и расходилась с фактическим состоянием кода;
- не было отдельного компонентного теста, который явно фиксирует критичный сценарий выбора/активации версии шаблона (в рамках потока «Работа с шаблонами»);
- отсутствовал единый «честный» список текущих пробелов до полного v1-ready (особенно по глубине сценариев, а не по наличию страниц).

## 3) Что реализовано в этой задаче

1. **Актуализирована документация фронтенда**
   - `docs/FRONTEND_GAP_ANALYSIS.md`
   - `docs/FRONTEND_ARCHITECTURE.md`
   - `docs/FRONTEND_ROUTES_AND_PERMISSIONS.md`
   - `docs/FRONTEND_TEST_PLAN.md`

2. **Добавлен тест критичного шаблонного сценария**
   - `src/__tests__/TemplateDetails.test.tsx`:
     - рендер версий шаблона;
     - проверка, что текущая версия неактивируема;
     - проверка возможности активации не-текущей версии;
     - проверка вызова `activateVersion(templateId, versionId)`.

3. **Подтверждено состояние quality gates**
   - lint/typecheck/test проходят в зелёном статусе.

## 4) Что ещё предстоит сделать до «полного v1-ready»

Кодовая база уже близка к MVP+, но для полного соответствия ТЗ целесообразно закрыть следующие крупные блоки:

1. **Глубина доменных workflow**
   - полноценные карточки/детали + связанные действия (не только реестры);
   - расширенные массовые операции и сценарии эскалации/делегирования в ЭДО.

2. **Унификация табличных паттернов**
   - единая серверная пагинация/сортировка/сохранённые представления во всех крупных реестрах.

3. **Матрица read-only поведения по ролям**
   - систематическое покрытие сценариев «аудитор/клиент только чтение» по всем доменам.

4. **E2E-контур критических процессов**
   - мастер пакета документов end-to-end;
   - архив/поиск + сохранённые представления;
   - клиентский портал (изоляция данных) в browser-level тестах.
