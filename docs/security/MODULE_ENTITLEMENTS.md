# SEC-63 (разд. 63.3): модульный доступ как поверхность атаки

ТЗ: «Модульный доступ (Доп. №2, разд. 61) сам может стать вектором, если сделан
только на фронте». Ниже — вердикт по каждому из трёх названных рисков.

## Риск 1: обход через прямой API — ЗАКРЫТ

> «Выключенный на фронте модуль доступен по прямому вызову API. → Enforcement на
> backend обязателен».

Все восемь модулей каталога (`FEATURE_CATALOG`) проверяются на бэкенде через
`is_feature_enabled` и отвечают **404** при выключенном модуле:

| Модуль | Где стоит гейт |
|---|---|
| `committees` | `api/routes/committees.py` |
| `contractors` | `api/routes/contractors.py` |
| `medical` | `api/routes/medical/_common.py` |
| `report_builder` | `modules/report_builder/api.py` |
| `budget` | `modules/budget/api.py`, `modules/budget/reimbursement_api.py` |
| `sout` | `api/routes/sout.py` |
| `rules_engine` | `modules/rules_engine/api.py` **и** `engine.py` |
| `warehouse` | `api/routes/ppe.py`, `modules/ppe/stock.py` |

**Чего не хватало:** ничто не мешало добавить девятый модуль и забыть гейт — тогда
«отключённый» модуль остаётся доступным всем, у кого есть токен, и заметить это
можно только пентестом. Ратчет-гард `scripts/ci/check_module_gates.py` (шаг в
`ci.yml`) требует backend-гейт у каждого кода каталога.

## Риск 2: эскалация через зависимости — НЕПРИМЕНИМ СЕЙЧАС

> «Включение модуля-зависимости открывает больше, чем ожидалось. → Проверка
> `depends_on` не должна тихо включать лишнее».

Зависимостей между модулями в каталоге **нет**: `apply_plan` переключает флаги
строго по списку тарифа, ничего не «дотягивая». Риск неприменим — но не навсегда:
гард падает, если в `modules/subscription/plans.py` появится любая константа с
`DEPEND` в имени. Тогда решение об обработке зависимостей придётся принять
осознанно, а не унаследовать молчанием.

## Риск 3: осиротевшие доступы — ЧАСТИЧНО

> «После отключения модуля остаются активные API-ключи/вебхуки/задачи этого
> модуля. → Отключение модуля деактивирует связанные интеграции».

**Что закрыто.** Правила автоматизации (`rules_engine`) проверяют флаг **в момент
исполнения** (`modules/rules_engine/engine.py`), а не только при создании правила,
поэтому после отключения модуля они перестают срабатывать сами.

**Что НЕ закрыто и почему.** Вебхуки и API-ключи **не привязаны к модулям**: у
`WebhookEndpoint` есть список `subscribed_events`, но типы событий не отображаются
на коды модулей один к одному (`DocumentGenerated`, `PPEIssued`,
`TrainingCompleted` — сквозные, а каталог модулей другой). «Деактивировать
связанные интеграции» невозможно, пока такой привязки нет; вводить её задним
числом, угадывая соответствие, значит с высокой вероятностью отключить лишнее у
работающих арендаторов.

Правильный порядок — отдельной задачей:

1. добавить модулю в каталоге список типов событий, которые он порождает;
2. на отключении модуля убирать эти типы из `subscribed_events` подписок и гасить
   эндпоинты, у которых не осталось событий;
3. то же для API-ключей, когда у них появится scope по модулям.

До этого остаточный риск такой: у арендатора, потерявшего модуль при понижении
тарифа, продолжает работать ранее настроенный вебхук на события этого модуля.
Данные уходят на адрес, который арендатор сам когда-то указал, — то есть это не
утечка третьему лицу, а невыполненное обещание «модуль выключён».

## Разделы 63.1 и 63.2

Не реализуемы **сейчас**, и это не отговорка: обе угрозы описывают функции,
которых в продукте ещё нет.

* **63.1 Иерархия Reseller → Client** — сама иерархия относится к BIZ-52 (Phase 13,
  статус `partial(branding)`). Тестировать «cross-reseller deny» не на чем.
* **63.2 Impersonation** — «работа в контексте клиента» относится к BIZ-49
  (Managed Clients, статус `missing`).

Когда эти функции появятся, требования разд. 63 — обязательная часть их
приёмки, а не отдельная задача «потом»: ограничение по времени сессии,
несмываемый аудит «X от имени Y», запрет смены паролей/платёжных данных/массового
экспорта ПДн из-под имперсонации, согласие клиента на делегированный доступ.
