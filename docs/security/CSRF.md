# SEC-64 (разд. 64.1): CSRF — модель и принятые меры

ТЗ требует: «CSRF: Anti-CSRF токены для cookie-сессий; SameSite; **проверка Origin
для мутаций**». Ниже — вердикт по каждому пути аутентификации, а не общее «у нас
Bearer, значит неприменимо».

## Где CSRF применим, а где нет

| Путь аутентификации | Как передаётся секрет | CSRF применим? |
|---|---|---|
| Основной API | заголовок `Authorization: Bearer` | **Нет.** Браузер не проставит чужой заголовок сам; кросс-сайтовый запрос уйдёт без токена и получит 401 |
| Клиентский портал | заголовок `X-Portal-Token` или query | **Нет** по той же причине |
| `POST /auth/refresh` | **cookie** `refresh_token` | **Да.** Cookie браузер подставляет сам — это единственная мутация, которую можно вызвать, не имея доступа к токену |

То есть распространённый вывод «CSRF неприменим, потому что Bearer» здесь неверен:
обновление сессии живёт на cookie.

## Что защищает `/auth/refresh`

1. **`SameSite=Strict`** — cookie не отправляется при кросс-сайтовом запросе.
2. **`HttpOnly`** — токен недоступен скриптам, XSS его не прочитает.
3. **`Secure`** — только по HTTPS.
4. **Path-скоуп** — cookie уходит только на путь обновления, а не на каждый запрос.
5. **Проверка `Origin` (добавлена)** — `app/core/csrf.py::assert_trusted_origin`.

Почему пятого пункта было недостаточно без него: `SameSite` **выставляет сервер, а
соблюдает клиент**. Старый браузер, нестандартный HTTP-клиент или будущее изменение
поведения атрибута снимают защиту целиком, и сервер об этом не узнает. `Origin`
проверяет сервер — это независимый второй рубеж, ровно его ТЗ и называет.

## Почему проверка узкая

`assert_trusted_origin` вызывается **только когда refresh-токен взят из cookie**.
Требовать `Origin` от всех мутаций нельзя: серверные API-клиенты его не шлют, и
такой гард сломал бы интеграции, не добавив защиты (Bearer-запрос кросс-сайтом не
подделать). Клиент, передающий токен в **теле** запроса, проходит без `Origin` —
это осознанный, протестированный сценарий.

Отсутствие `Origin` у cookie-запроса — отказ: современные браузеры шлют этот
заголовок на всех небезопасных методах, включая same-origin, поэтому его отсутствие
само по себе аномально. `Referer` принимается как запасной вариант.

Источник сравнивается как `scheme://host:port` со списком `APP_CORS_ORIGINS`; путь и
строка запроса игнорируются, сравнение регистронезависимое и **не** подстрочное
(`https://app.example.com.evil.tld` не пройдёт).

## Anti-CSRF токены

Отдельный синхронизирующий токен **не вводится**: он имеет смысл для cookie-сессий,
которыми аутентифицируется весь трафик. Здесь на cookie живёт одна ручка, и она
закрыта комбинацией `SameSite=Strict` + `Origin`. Вводить токен-синхронизатор ради
одного эндпоинта — усложнение без выигрыша; решение зафиксировано здесь, чтобы при
появлении полноценных cookie-сессий его пересмотрели осознанно.
