# SEC-68: внешний контур и клиентский портал

Внешние пользователи (клиенты, подрядчики) — за периметром, их устройства не
контролируются, а вход в портал — это один токен в ссылке. Разд. 68 требует
разворачивать «безопасную ссылку» в модель угроз, а не в заклинание.

## Модель угроз magic link (разд. 68.1) и что ей противопоставлено

| Угроза | Мера | Состояние |
|---|---|---|
| Перебор токена | криптостойкий токен ≥128 бит, не последовательный | `secrets.token_urlsafe(24)` = **192 бита** ✅ |
| Перебор в лоб (скорость) | отдельный anti-abuse на внешнем контуре | счётчик неудач по IP ✅ |
| Утечка через логи | токен не попадает в структурный лог | логируется `path` без query ✅ |
| Утечка через Referer/историю браузера | токен не в query | ⚠️ **частично**: query всё ещё принимается ради уже разосланных ссылок |
| Бессрочный доступ | обязательный TTL, отзыв, привязка к ресурсу | `expires_at` + потолок TTL, `revoked_at`, `scope_json` ✅ |
| Пересылка ссылки третьему лицу | одноразовость где возможно | `max_uses` / `uses_count` ✅ |
| Пересылка (усиленная) | привязка к получателю (email/OTP) | ❌ не реализовано — нужен канал доставки OTP |

## Anti-abuse (разд. 68.2)

Два независимых счётчика, оба по IP, оба жёстче внутренних лимитов:

| Настройка | Умолчание | Что ограничивает |
|---|---|---|
| `PORTAL_RATE_LIMIT_PER_IP` | `60/minute` | общий поток портальных запросов |
| `PORTAL_AUTH_FAILURES_PER_IP` | `10/hour` | **неудачные** попытки по токену |

Разделение принципиально: счётчик неудач тратят только неверные токены, поэтому
порог можно держать низким — легитимный клиент его не касается. Проверка блокировки
идёт **до обращения к базе**, иначе каждая попытка перебора стоила бы нам запроса в БД.

Протухшая или отозванная ссылка **не** считается попыткой перебора: это обычная
ситуация у клиента со старым письмом, и штрафовать его за это нельзя.

**Хранилище счётчиков** — то же, что у основного лимитера (`RATE_LIMIT_STORAGE_URI`).
На `memory://` счётчики процесс-локальны: при нескольких воркерах фактический порог
умножается на их число. Для внешнего контура в проде **нужен Redis**.

## Срок жизни ссылки

| Настройка | Умолчание | Смысл |
|---|---|---|
| `PORTAL_TOKEN_TTL_HOURS` | `24` | сколько живёт выданная ссылка |
| `PORTAL_TOKEN_MAX_TTL_HOURS` | `168` | потолок: «вечную» ссылку нельзя выдать даже опечаткой в конфиге |

## Одноразовые ссылки

`POST /api/v1/packages/runs/{run_id}/portal-link?max_uses=1` — строго одноразовая
ссылка. Без параметра лимита нет (поведение всех ранее выданных ссылок, поэтому
бэкфилл не нужен). Счётчик растёт при каждой успешной проверке, поэтому пересланная
копия исчерпывает тот же лимит, что и оригинал; `last_used_at` отвечает на вопрос
«ходили ли по ссылке после того, как подрядчик уволился».

## Известный остаток

**Токен в query.** Разд. 68.1 предпочитает заголовок или тело: query-строка утекает в
Referer, историю браузера и access-логи обратного прокси (в наш структурный лог она
не попадает — там только `path`). Портал принимает и заголовок `X-Portal-Token`, и
`?token=`; убрать query нельзя одним коммитом, потому что уже разосланные клиентам
ссылки перестанут открываться. Правильный переход — обмен: ссылка с `?token=` ведёт
на страницу, которая один раз меняет его на короткоживущий сеансовый токен в теле
ответа, дальше только заголовок. Это затрагивает фронтенд и вынесено в отдельную
задачу.

**Привязка к получателю (OTP).** Разд. 68.1 предлагает опционально; требует канала
доставки одноразового кода (e-mail/SMS) и отдельного UX.
