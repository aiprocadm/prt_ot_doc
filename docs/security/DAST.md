# SEC-69 (разд. 69.1): динамический скан (DAST)

ТЗ: «DAST (динамика) — НЕТ → **Добавить базовый (OWASP ZAP) на стенде**».

Статический анализ (bandit, semgrep) читает код, Trivy — зависимости. Ни тот, ни
другой не видит, что реально отвечает работающее приложение: заголовки, коды
ошибок, поведение на неожиданном вводе. Это и закрывает DAST.

## Как устроено

Workflow `.github/workflows/dast.yml`:

1. выгружает **полную спецификацию OpenAPI** — `scripts/ci/dump_openapi.py`;
2. поднимает приложение в dockerless-режиме на SQLite и ждёт `/health`;
3. запускает `zaproxy/action-api-scan`: спецификация берётся из файла, запросы
   уходят на живое приложение (`-O http://127.0.0.1:8000`);
4. складывает отчёт (HTML/JSON/MD) и лог бэкенда в артефакты на 30 дней.

### Почему спецификация из файла, а не с живой ручки

`/api/openapi.json` доступна не всегда: в production документация отключена
намеренно (`_disable_openapi_in_production`), в dockerless-запуске её тоже нет, а
сама ручка требует заголовок `X-Tenant`. Сканер не получил бы список эндпоинтов
раньше, чем настроен на аутентификацию. Вызов `app.openapi()` даёт полный набор
путей независимо от того, что сервер решил показывать наружу — на момент внедрения
это **683 пути и 909 операций**.

### Почему заголовок тенанта подставляется сканеру

Без `X-Tenant` каждый запрос отбивает `TenantMiddleware`, и скан проверил бы ровно
один обработчик ошибки. Заголовок задаётся через ZAP replacer в `cmd_options`.

## Почему по расписанию, а не на каждый PR

Скан обходит 900+ операций — это минуты, и находки повторяются от прогона к
прогону. Еженедельный запуск плюс кнопка `workflow_dispatch` дают ту же информацию,
не удлиняя цикл разработки. Тест `test_workflow_does_not_run_on_every_pull_request`
это фиксирует, чтобы решение не «уехало» незаметно.

## Почему observe-mode

`fail_action: false`. Базовый прогон на живом API всегда даёт шум (информационные
предупреждения ZAP), и блокирующий гейт на старте означал бы красный пайплайн и
последующее отключение проверки — тем же путём в репозитории поэтапно вводились
semgrep и pip-audit (см. `docs/security/DEPENDENCY_AUDIT.md`).

### Порядок перевода в блокирующий

1. Прогнать по расписанию 2–3 раза, собрать повторяющиеся находки.
2. То, что для JSON-API неинформативно, — в `.zap/rules.tsv` **с комментарием**
   (тест требует комментарий у каждого правила: подавление без объяснения через
   полгода превращается в «почему тут молчит?»).
3. Реальные находки — исправить или внести в `.github/security-exceptions.yml`
   с обоснованием и сроком пересмотра.
4. Снять `fail_action: false`.

## Что остаётся по разд. 69

- **semgrep** пока в observe-mode — по тому же плану.
- **Пентест перед продом с ПДн** — организационная мера, не автоматизируется.
  Фокус по ТЗ: изоляция арендаторов, иерархия reseller, impersonation, внешний
  контур, документный пайплайн.
- **Security Definition of Done** (разд. 69.2, «седьмой вопрос»): константа
  `SECURITY_QUESTION` в `core/product_spec.py` есть, но ничем не проверяется.
  Ввод такого гейта меняет процесс ревью, поэтому предлагается, а не навязывается.

## Локальный прогон

```bash
PYTHONPATH=backend python scripts/ci/dump_openapi.py --output openapi.json
PYTHONPATH=backend python scripts/run_backend_lite.py &
docker run --rm -v "$PWD:/zap/wrk:rw" --network host ghcr.io/zaproxy/zaproxy:stable \
  zap-api-scan.py -t openapi.json -f openapi -O http://127.0.0.1:8000 -c .zap/rules.tsv
```
