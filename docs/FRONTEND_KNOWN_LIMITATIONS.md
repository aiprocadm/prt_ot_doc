# FRONTEND_KNOWN_LIMITATIONS

Ниже только реальные ограничения, которые остаются backend-dependent.

1. **Upload progress granularity**
   - Сейчас frontend показывает этапный прогресс (uploading/processing/ready/error).
   - Для точного серверного прогресса нужен backend канал прогресса (SSE/WebSocket/подробный polling contract).

2. **Domain-level structured API errors**
   - Для некоторых сценариев (редкие edge-cases в jobs/edo) сервер возвращает ограниченный `message` без унифицированного `details`.
   - Это снижает точность контекстных UX-подсказок при нештатных ошибках.

3. **Cross-tenant E2E on CI**
   - Unit/integration слой покрывает tenant-aware подготовку запросов.
   - Полный browser-level тест c переключением tenant и проверкой изоляции зависит от стабильного CI-стенда с подготовленными данными для нескольких контуров.


4. **Нестабильность локального test-runner под нагрузкой**
   - В текущем контейнере периодически наблюдаются зависшие zombie-процессы vitest/eslint, что увеличивает время прогона.
   - Это инфраструктурное ограничение окружения, не логики UI; в CI и чистом локальном запуске требуется отдельная верификация производительности test-runner.

5. **Act warnings в тест-раннере React 18**
   - В части интеграционных тестов остаются предупреждения `act(...)` от Radix/React Router transitions.
   - Это не влияет на прохождение тестов, но для полного «чистого» вывода требуется точечная переработка async-ожиданий в legacy тестах.

## Статус после текущего прохода
- Проблема с `typecheck` из-за теста загрузки файлов устранена и больше не является ограничением.
- Flaky ожидание lazy-route в smoke-тесте маршрутизации устранено и больше не относится к известным ограничениям.

## Дополнение по текущему проходу

6. **Шум `act(...)` warnings в тестах с тяжёлой асинхронностью**
   - В ряде интеграционных тестов (`FileUploader` и часть маршрутов) остаются предупреждения React 18 о `act(...)` из-за каскадных async-update внутри сторонних библиотек.
   - Это не блокирует прохождение `vitest`, но для полностью «чистого» лога нужен отдельный рефактор async-ожиданий и, местами, адаптация тестовых двойников Radix/Dropzone.

## Обновление по маршрутам/изоляции
- Ограничение с некорректным fallback-маршрутом снято: по умолчанию используется динамический landing-route по доступным разрешениям.
- Ограничение с «админским» сайдбаром в portal-only контуре снято: клиентский кабинет изолирован на уровне структуры навигации.
