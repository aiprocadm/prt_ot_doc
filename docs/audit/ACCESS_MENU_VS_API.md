# Меню и права ручек: где они расходятся

Разбор от 2026-09-13 (срез-166). Кода не меняет: это рабочий лист для решения
владельца. Вопрос «кому что можно» — не инженерный, поэтому здесь только
измерения и проверенные примеры.

## Коротко

Три разных расхождения, у каждого своя причина:

1. **Пункт меню виден, ручка отказывает.** Человек видит раздел, заходит и
   получает «нет доступа». Так ведут себя 51 пункт из 77.
2. **Словари прав у сервера и витрины почти не пересекаются.** Сервер выдаёт
   роли 119 разных кодов прав, витрина узнаёт из них 13. Десять кодов имеют
   очевидную пару и просто не связаны между собой.
3. **Один отказ роняет сводный экран целиком.** Плитки грузятся одним пакетом
   без запасного пути: если хоть одна ручка ответила отказом, пустеет вся
   страница, а не одна плитка.

## Как измерялось

Приложение собиралось живьём, обходились все 1128 маршрутов; у 911 из них
роли доставались из самой проверки доступа (замыкание `rbac`). Проверка на
заведомо известной ручке сошлась: исходящая очередь доступна только `admin`.
Меню читалось из `frontend/src/router/navigationConfig.ts` (77 пунктов), права
роли — так же, как их считает сама витрина: список от `/auth/me` главнее, роли
`admin` и `owner` видят меню целиком по отдельному правилу.

Числа получены разбором, поэтому каждый вывод ниже я проверял вручную по коду;
отклонённые кандидаты перечислены в конце.

## 1. Первый экран после входа

`GET /dashboard/summary` разрешён ролям:

| Разрешено | Не разрешено, но пункт «Главная» виден |
| --- | --- |
| admin, owner, line_manager, hr, ot_pb_lead | ot_specialist, pb_engineer, accountant, contractor_inspector, student, worker |

Специалист по охране труда — основной пользователь продукта — на первом же
экране получает отказ. То же у «Командного центра».

## 2. Старые реестры, прибитые к одному `admin`

Восемнадцать разделов перечисляют в правах только `admin`, хотя пункт меню
видят профильные роли. Самые заметные: сотрудники, филиалы, площадки,
шаблоны, инциденты, проверки и предписания (оба контура), комитеты, СОУТ,
допуски, наряды-допуски, СИЗ и склад СИЗ, инструктажи, медосмотры.

Пример: `GET /api/v1/incidents` — только `admin`, а пункт «Инциденты / НС»
видят восемь ролей, включая специалиста по ОТ и инженера по промбезопасности.

## 3. Контур согласований и ЭДО

`GET /approvals`, `/approval-routes`, `/sign/requests`, `/edo/messages`
пускают только `admin` и `employee`. Пункты меню видят 16 ролей.

## 4. Словари прав говорят на разных языках

Сервер выдаёт коды вида `trainings:read`, витрина знает `training.view`.
Связывает их таблица синонимов, в ней 37 строк — на 119 кодов сервера.

Десять кодов имеют однозначную пару и не связаны только по недосмотру:

```
contractors.list, contractors.read  -> contractor.view
files.list                          -> file.view
incidents.list                      -> incident.view
inspections.list                    -> inspection.view
reports.list, reports.read          -> reports.view
templates.list                      -> template.view
trainings.list, trainings.read      -> training.view
```

**Почему я не стал их связывать сам.** Связать — значит показать человеку
больше пунктов меню. Но у части этих разделов ручка всё равно пускает только
`admin` (пункт 2), и тогда починка одного расхождения увеличит другое: пунктов
станет больше, отказов — тоже. Сначала нужно решение по правам ручек.

## 5. Обратная сторона

Есть и зеркальный случай: сервер пускает, а меню прячет. Роли `hr` и
`line_manager` допущены к сводке главной, но пункт «Главная» им не виден —
их права приходят кодами, которых нет в таблице синонимов.

## Что нужно решить владельцу

1. **Кто должен открывать главную сводку?** Если специалист по ОТ и инженер по
   ПБ должны — расширяем список ролей ручки. Если нет — убираем пункт из их
   меню, иначе первый экран после входа всегда отказ.
2. **Восемнадцать разделов с одним `admin`** — оставить как есть (тогда прятать
   пункты) или открыть профильным ролям (тогда расширять ручки).
3. **Согласования и ЭДО** — та же развилка для 16 ролей.
4. **Кто ведёт словарь прав?** Пока их два и они расходятся. Либо витрина
   переходит на коды сервера, либо таблица синонимов становится обязательной
   и закрывается сторожем.

После решения по пунктам 1–3 работа механическая, и её можно закрыть сторожем
«пункт меню виден ровно тем, кого пускает ручка».

## Отклонённые кандидаты

Проверены вручную и расхождением НЕ являются:

- **Клиенты и подписки, Бренд** — роль проверяется не зависимостью, а внутри
  тела обработчика (`_MANAGEMENT_ROLES`), и пункт виден ровно тем же ролям.
- **Синхронизация (offline)** — экран не обращается к серверу вовсе.
- **Состояние системы, Архив и поиск, Центр внимания, Уведомления, Обучение,
  Клиенты (аутсорсинг), НПА, Реестр требований, Операции** — у ручек нет
  ролевого гейта, пускают любого вошедшего.
- **Контуры дисциплин** (пожарная безопасность, промбезопасность, экология,
  ГО и ЧС, БДД), календарь, риски, качество данных, экспорты, управленческая
  аналитика, KPI комитетов, бюджет — роли ручки шире или ровно совпадают с
  видимостью пункта. Это единственная зона, где витрина и сервер сходятся.
