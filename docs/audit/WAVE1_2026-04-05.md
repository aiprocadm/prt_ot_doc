## Production blockers (зафиксировано)

| ID | Описание | Где |
|----|----------|-----|
| PB-1 | В README/SETUP/OBSERVABILITY указан `celery -A backend.app.worker`, но `backend/app/worker.py` не экспортирует Celery app — воркер в Docker использует `app.services.celery_app`. Оператор не поднимет очереди по старым инструкциям. | Исправлено в Wave 1 |
| PB-2 | Локальная среда: проект заявляет Python **3.12** (Dockerfile, CI); на машине без 3.12 `pip install` / тесты могут не воспроизводиться (например, только 3.13). | Документировать в SETUP явное требование 3.12 или использовать Docker |

## Security (зафиксировано)

| ID | Описание | Риск |
|----|----------|------|
| SEC-1 | `TenantContext.roles` заполнялись из заголовка `x-roles` даже при наличии Bearer; контекст мог расходиться с JWT и давать ложную картину в логах/будущих проверках. Авторизация в основном идёт через `AccessContext`/JWT, но дублирование источников — техриск. | Снижен в Wave 1: при наличии токена роли контекста только из claims |
| SEC-2 | Слабые пароли и `SECRET_KEY=change-me` в `.env.example` — ожидаемо для dev; в production обязательна замена (уже описано в комментариях `.env.example`). | Операционный |

## Data integrity / архитектура (кратко)

- Tenant middleware сверяет `X-Tenant` с claim `tenant` в JWT — хорошая защита от подмены тенанта при валидном токене.
- CI: шаг Alembic выполняет `alembic heads` против SQLite — проверяет отсутствие «раздвоенных» head, но **не** прогоняет `upgrade head` на реальной схеме; при ошибках в миграциях возможен пропуск до staging.
